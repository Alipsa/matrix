# matrix-groovy-ext v0.4.1 fixes

Findings from a review of `NumberExtension` and the module build at `0.4.1-SNAPSHOT`
(commit `74369611`). Organized into PR-sized sections, ordered: correctness bugs
first, then performance, then build metadata, then release wrap-up.

**Goal:** Close two verified accuracy defects (`log` family just below 1; `sin`/`cos`/`tan`
near their zeros), remove a performance cliff in `log1p`, stop `tan` from reducing its
angle twice, and fix the broken POM URLs — without changing any currently correct
numeric value.

**Architecture:** Both accuracy defects have the same root cause. A fixed DECIMAL128
calculation leaves an *absolute* error of about 1e-33. When the true result is close to
zero, that becomes a large *relative* error, which breaks the DECIMAL64 result contract.
- `log`: `lnSeries` rescales inputs in `[0.5, 1)` by a power of ten and then adds back
  `k·ln(10) + m·ln(2)`, terms of size ~2 that cancel when `ln(x) ≈ 0`.
- Trigonometry: `reduceAngle` reduces only modulo 2π, so the Taylor series runs on the
  unreduced distance to the zero and cannot represent a tiny result relatively.

The fixes are to skip the cancelling reduction for `log`, and to reduce trigonometric
arguments modulo π/2 with an adaptive π precision.

**Tech Stack:** Groovy 5.1.1, Java 21 target, JUnit Jupiter 6.0.3, groovier-junit.

**Source of findings:** code review of `NumberExtension.groovy`. Every numeric claim was
checked against a 40–60 digit `BigDecimal` reference. Every fix below was prototyped in a
scratch worktree. With the prototype, `codenarcMain`, `codenarcTest`, `spotlessCheck` and
`:matrix-groovy-ext:test` all pass: 76 tests, 70 existing and 6 new. Five of the new tests
target bugs, and the sixth is a regression guard that passes on both versions. Four of the
bug tests were run against the current code and fail there. The fifth
(`testExactHalfPiAtPrecisionCapGivesCanonicalZeroAndTangentError`) was not; its failure is
inferred from a direct probe of the current jar. Task 2.1's "run them first" step confirms
it. See **Notes for the implementer** for the evidence.

**Revision 2** addresses a review of this plan:
- `tan` gets an accurate exception message and corrected GroovyDoc on both overloads.
- `cos`/`sin` return a canonical zero for an exactly zero remainder.
- The cache-touching tests restore `cachedPi`.
- The reduction loop doubles its precision when it stalls; it previously crept 43 → 512 in
  22 passes.
- Release-note heading ownership is clarified, the POM check is stricter, and the version
  bump now covers `build.gradle`.

**Revision 3** keeps the retry arithmetic in `long` (§2.3), writes the stall test as
`2 * gain < increase`, which is slightly stricter for odd increases (§2.3), makes the
exact-π/2 test use the production rounding mode (§2.1), and stops the summary from
overstating which tests were run.

# Part A — Correctness bugs

## 1. Fix `log` / `log10` / `log(x, base)` cancellation just below 1

`lnSeries` (`NumberExtension.groovy:206`) always rescales by a power of ten. A value in
`[0.5, 1)` gets `tenPower = -1` and then `twoPower = 2` or `3`. For example, 0.99 gives
`twoPower = 3`, and the result is assembled as `2·atanh(y) − ln(10) + 3·ln(2)`. Those
terms are about 2 in size, so their ~1e-33 rounding error swamps a result near zero.
Measured on `0.4.1-SNAPSHOT`:

```
log(1 - 1e-18)       actual -9.99999999999985E-19   expected -1.000000000000000E-18
log(1 - 1e-20)       actual -9.999999999986E-21     expected -1.000000000000000E-20
log(1 - 1e-25)       actual -9.9999985E-26          expected -1.000000000000000E-25
log10(1 - 1e-25)     actual -4.342944167590795E-26  expected -4.342944819032518E-26
2G.log(1 - 1e-25G)   actual -6.931472845320380E+24  expected -6.931471805599453E+24
```

Values above 1 are unaffected, because `[1, 2]` already gets `tenPower = 0`. `log1p` is
unaffected for `|x| < 1e-10` (it uses `log1pSmall`), and for `x <= -1e-10` the result is
no smaller than 1e-10, so the error stays below DECIMAL64 resolution.

## 2. Quadrant reduction with adaptive π precision for `sin` / `cos` / `tan`

`reduceAngle` (`NumberExtension.groovy:752-775`) leaves `|angle| <= 2π` unreduced. For
`|angle|` up to 13 integer digits it uses `angle.remainder(TWO_PI)` with a 31-digit π.
`sinInternal`/`cosInternal` then sum a Taylor series at a fixed DECIMAL128 precision.
Near the zeros of `sin`/`tan` (multiples of π) and of `cos` (odd multiples of π/2), that
~1e-33 absolute error dominates. Measured on `0.4.1-SNAPSHOT`:

```
sin(NumberExtension.PI32)        actual 5.036857630569771E-31   expected 5.028841971693994E-31   (wrong at the 3rd digit)
sin(3.141592653589793238462643)  actual 3.832795019197533E-25   expected 3.832795028841972E-25
cos(π/2 to 25 digits)            actual -3.083602480167727E-25  expected -3.083602485579014E-25
tan(3.141592653589793238462643)  actual -3.832795019197533E-25  expected -3.832795028841972E-25
```

Angles derived from a `double` (such as `Math.PI`) are at least ~1e-16 from a zero and
are not affected. This section also fixes the review's **finding 5**: `tan` calls
`sinInternal` and `cosInternal`, so it reduces the same angle twice (`:1061-1062`).

**Approach:**
- Reduce to `r = angle − k·π/2` with `|r| <= ~π/4` and `quadrant = k mod 4`. Start at the
  existing precision rule (`integerDigits + 34 + 8`).
- If `r` is within `REDUCTION_GUARD_DIGITS` (19) orders of magnitude of the reduction
  error bound `10^(integerDigits + 1 − precision)`, retry with enough extra π digits to
  close the shortfall (at least `REDUCTION_PRECISION_STEP`).
- If a retry gained less than half the digits it added, the remainder is dominated by the
  reduction error and shrinks with it. Double the precision instead of creeping. For
  `pi600.sin()` this cuts 22 passes to 5, and the cold-cache time from 285 ms to 42 ms.
- Cap the retries at `MAX_TRIGONOMETRIC_PRECISION` (512). Beyond the cap the result is best
  effort. `sin` and `cos` never throw there, and an exactly zero remainder is returned as
  canonical `BigDecimal.ZERO`, so results are `0` rather than `0E-511`.
- **One new exception path, in `tan` only.** An angle that equals `k·π/2` (k odd) to all
  512 digits, such as `calculatePi(512)/2`, reduces to an exactly zero remainder in an odd
  quadrant. `tan` then has a zero denominator and throws
  `ArithmeticException('Tangent undefined (angle reduces to an exact multiple of π/2)')`.
  Today the same input returns finite noise (`2.068874630406508E+33`). This is recorded in
  release.md (2.6).
- Keep the existing rejection rule and message unchanged:
  `integerDigits + 42 > 512 → ArithmeticException`, with the `1E+469` / `1E+470`
  boundary.

2.3 [x] Replace `reduceAngle` (`NumberExtension.groovy:752-775`, GroovyDoc included) with
  the `ReducedAngle` holder and `reduceToQuadrant`:

```groovy
  /** An angle reduced to {@code remainder = angle - k * π/2} with {@code quadrant = k mod 4}. */
  private static final class ReducedAngle {

    final BigDecimal remainder
    final int quadrant

    ReducedAngle(BigDecimal remainder, int quadrant) {
      this.remainder = remainder
      this.quadrant = quadrant
    }

  }

  /**
   * Reduces an angle modulo π/2 so the Taylor series run on {@code |remainder| <= ~π/4}.
   * <p>The π precision starts from the integer part of the angle and grows while the remainder is
   * within {@link #REDUCTION_GUARD_DIGITS} orders of magnitude of the reduction error bound, so
   * angles close to a multiple of π/2 keep DECIMAL64 relative accuracy. Growth is capped at
   * {@link #MAX_TRIGONOMETRIC_PRECISION}; beyond the cap the reduction is best effort.
   */
  private static ReducedAngle reduceToQuadrant(BigDecimal angle) {
    if (angle.abs() <= QUARTER_PI) {
      return new ReducedAngle(angle.round(CALCULATION_CONTEXT), 0)
    }

    long integerDigits = Math.max(1L, (angle.precision() as long) - angle.scale())
    long requestedPrecision = integerDigits + CALCULATION_CONTEXT.precision + 8
    if (requestedPrecision > MAX_TRIGONOMETRIC_PRECISION) {
      throw new ArithmeticException("Angle magnitude is too large for trigonometric range reduction: ${angle}")
    }

    int precision = requestedPrecision as int
    long previousSeparation = 0
    long previousIncrease = 0
    while (true) {
      MathContext context = new MathContext(precision, RoundingMode.HALF_EVEN)
      BigDecimal halfPi = calculatePi(context).divide(TWO, context)
      BigDecimal quotient = angle.divide(halfPi, context).setScale(0, RoundingMode.HALF_EVEN)
      BigDecimal remainder = angle - quotient * halfPi
      boolean zeroRemainder = remainder.signum() == 0
      // |reduction error| <= |quotient| * ulp(halfPi) <= 10^(integerDigits + 1 - precision)
      long errorExponent = integerDigits + 1 - precision
      long separation = zeroRemainder ? 0 : (remainder.precision() as long) - remainder.scale() - 1 - errorExponent
      if ((!zeroRemainder && separation >= REDUCTION_GUARD_DIGITS) || precision >= MAX_TRIGONOMETRIC_PRECISION) {
        int quadrant = Math.floorMod(quotient.remainder(FOUR).intValue(), 4)
        return new ReducedAngle(zeroRemainder ? BigDecimal.ZERO : remainder.round(CALCULATION_CONTEXT), quadrant)
      }
      // A remainder dominated by reduction error shrinks with that error, so its separation stops
      // growing with precision. Double the precision then instead of creeping towards the cap.
      boolean stalled = previousIncrease > 0 && 2 * (separation - previousSeparation) < previousIncrease
      long increase = stalled ? precision : Math.max(REDUCTION_PRECISION_STEP as long, REDUCTION_GUARD_DIGITS - separation + 2)
      previousSeparation = separation
      previousIncrease = increase
      precision = Math.min(MAX_TRIGONOMETRIC_PRECISION as long, precision + increase) as int
    }
  }
```

  Implementation notes:
  - `angle - quotient * halfPi` is exact. Groovy's BigDecimal `*` and `-` don't round, so
    the only error comes from `halfPi`, as the comment's bound states.
  - `quotient.remainder(FOUR)` is in `(−4, 4)`, and `Math.floorMod` maps negative angles
    to quadrants `0..3`.
  - When `quotient` lands on the wrong side of a `.5` boundary, `r` is still about π/4, so
    the result stays correct.
  - All retry arithmetic stays in `long`, and only the result, clamped to 512, is narrowed
    to `int`. Revision 2 cast `REDUCTION_GUARD_DIGITS - separation + 2` to `int`. A
    separation near `-Integer.MAX_VALUE` would then wrap `precision + increase` negative,
    and `new MathContext(negative)` would throw `IllegalArgumentException`. That would need
    an angle with about 2·10⁹ digits, so it is unreachable in practice, but `long` costs
    nothing. The stall test is written `2 * gain < increase`, so it needs no `intdiv` on a
    `long`.
  - That form is intentionally slightly stricter than revision 2's
    `gain < increase.intdiv(2)` when `increase` is odd. For example, with `increase = 23`
    and a gain of 11, revision 2 did not count a stall and revision 3 does. Doubling can
    therefore start earlier. This affects speed only. The accuracy guarantee is unchanged,
    since the exit condition (`separation >= REDUCTION_GUARD_DIGITS` or the cap) is the
    same. A different stall pass can still finish at a different precision, and the two
    remainders then differ beyond the guarantee. In principle, a DECIMAL64 result within
    about 1e-19 (relative) of a rounding boundary could differ by one ulp. No output
    differences were observed in the sweep, and no input that differs was searched for.
    The measured pass counts and results in the table below are the same under both forms.
  - Stall detection only triggers from the second pass (`previousIncrease > 0`). A genuine
    near-multiple gains about as many digits of separation as were added, so it never
    stalls. Measured pass counts with the doubling loop (with the earlier linear retry in
    parentheses):

    | Input                     | Passes   |
    |---------------------------|----------|
    | `sin(PI32)`               | 2 (2)    |
    | `sin(π to 101 digits)`    | 3 (5)    |
    | `sin(π to 160 digits)`    | 4 (8)    |
    | `pi600.sin()`             | 5 (22)   |

    The first three results match a 60–700-digit reference and are unchanged from the
    linear version. `pi600.sin()` is best effort at the cap (`-4.065664308602139E-512` in
    both versions; the true value is about 1e-600).
  - A zero remainder gets `separation = 0`, so the first retry adds the full shortfall (21).
    If the remainder is still zero on the next pass, the stall rule doubles the precision.

```groovy
  static BigDecimal sin(BigDecimal self) {
    ReducedAngle reduced = reduceToQuadrant(self)
    BigDecimal result = switch (reduced.quadrant) {
      case 0 -> sinSeries(reduced.remainder)
      case 1 -> cosSeries(reduced.remainder)
      case 2 -> sinSeries(reduced.remainder).negate()
      default -> cosSeries(reduced.remainder).negate()
    }
    result.round(RESULT_CONTEXT)
  }

  static BigDecimal cos(BigDecimal self) {
    ReducedAngle reduced = reduceToQuadrant(self)
    BigDecimal result = switch (reduced.quadrant) {
      case 0 -> cosSeries(reduced.remainder)
      case 1 -> sinSeries(reduced.remainder).negate()
      case 2 -> cosSeries(reduced.remainder).negate()
      default -> sinSeries(reduced.remainder)
    }
    result.round(RESULT_CONTEXT)
  }

  static BigDecimal tan(BigDecimal self) {
    ReducedAngle reduced = reduceToQuadrant(self)
    BigDecimal sinValue = sinSeries(reduced.remainder)
    BigDecimal cosValue = cosSeries(reduced.remainder)
    // tan(r + kπ/2) is tan(r) for even k and -cot(r) for odd k
    boolean evenQuadrant = reduced.quadrant % 2 == 0
    BigDecimal numerator = evenQuadrant ? sinValue : cosValue.negate()
    BigDecimal denominator = evenQuadrant ? cosValue : sinValue

    if (denominator == 0) {
      // Only an odd quadrant can reach this: cos(r) >= 0.707 for |r| <= π/4. It requires an angle
      // that equals k·π/2 to all 512 digits of the reduction cap, so the remainder is exactly zero.
      throw new ArithmeticException('Tangent undefined (angle reduces to an exact multiple of π/2)')
    }

    numerator.divide(denominator, CALCULATION_CONTEXT).round(RESULT_CONTEXT)
  }
```

# Part B — Performance

## 3. Stop `log1p` from expanding large inputs exactly

`log1p` computes `log(self + 1)` (`NumberExtension.groovy:325`) with an exact add. For
`1E+5000000` that first builds a 5,000,001-digit number. Measured: `log(1E+5000000)` takes
19 ms, `log1p(1E+500000)` takes 188 ms, and `log1p(1E+5000000)` takes 4084 ms; the cost
grows faster than the exponent. That is a denial-of-service risk for untrusted input.
Rounding the add to DECIMAL128 costs no accuracy: the argument's relative error is about
1e-34, which shifts the logarithm by about 1e-34 in absolute terms, below DECIMAL64
resolution for every result this branch can produce (`|log1p(x)| >= ~1e-10`).

3.1 [x] Add the failing test. Add the imports `org.junit.jupiter.api.Timeout` and
  `java.util.concurrent.TimeUnit`. Run it first and confirm it times out:

```groovy
  @Test
  @Timeout(value = 2, unit = TimeUnit.SECONDS)
  void testLog1pDoesNotExpandLargeInputs() {
    BigDecimal huge = new BigDecimal('1E+5000000')
    assertEquals(huge.log(), huge.log1p())
    [3.0G, -0.5G, 1e-10G, -1e-10G].each { BigDecimal x ->
      assertEquals((x + 1).log(), x.log1p(), "log1p(${x})")
    }
  }
```

  The 2 s limit leaves a wide margin: the fix takes ~22 ms and the current code ~4 s.
  `new BigDecimal('1E+5000000')` stays as written, because CodeNarc does not flag
  exponent-only strings and a `G` literal of that size is not practical.
3.2 [x] Replace `log(self + 1)` at `NumberExtension.groovy:325`:

```groovy
      log(self.add(BigDecimal.ONE, CALCULATION_CONTEXT))
```

3.3 [x] Record the change in `release.md` under the v0.4.1 heading (see 5.1): `log1p()`
  no longer expands very large inputs into an exact integer before taking the logarithm.
