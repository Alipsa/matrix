# matrix-groovy-ext v0.4.0 fixes

Findings from a review of `NumberExtension`. Organized into PR-sized sections,
ordered: correctness bugs first, then API contract, then performance, then
documentation.

**Goal:** Close four verified correctness defects in `NumberExtension`, make the
DECIMAL64 result contract uniform across every public method, and remove two
avoidable performance costs — without changing any currently correct numeric
value. Where DECIMAL64 rounding changes the scale or string representation of an
equal value, this plan calls that out explicitly and requires release documentation.

**Architecture:** Every transcendental in this class already follows one pattern:
compute at `CALCULATION_CONTEXT` (DECIMAL128) guard precision, round **once** to
`RESULT_CONTEXT` (DECIMAL64) on the way out. Four methods (`hypot`, `cbrt`,
`toDegrees`, `toRadians`) skip that pattern and lose last-place accuracy. The bulk
of this plan is bringing them into line, not inventing new numerics.

**Tech Stack:** Groovy 5.1.1, Java 21 target, JUnit Jupiter 6.0.3, groovier-junit.

**Source of findings:** code review of `NumberExtension.groovy` @ 0.4.0-SNAPSHOT,
with every numeric claim checked against a 40–200 digit `BigDecimal`/`Decimal`
reference. Reference values quoted in the tasks below are those measurements.

# Part A — Correctness bugs

## 1. Restore guard precision in `hypot()`

`hypot(BigDecimal, BigDecimal)` (`NumberExtension.groovy:695-711`) chains three
DECIMAL64 operations (`divide`, `sqrt`, `multiply`), so the guard digits are gone
before the final result is formed. Measured against a 40-digit reference:

```
hypot(123456789, 987654321)  actual 995340462.6258097   correct 995340462.6258100   (3 ulp)
hypot(1, 3)                  actual 3.162277660168380   correct 3.162277660168379
hypot(2, 5)                  actual 5.385164807134505   correct 5.385164807134504
```

The two zero-side early returns also skip the DECIMAL64 precision cap. Inputs with
more than 16 significant digits therefore escape unchanged instead of being rounded
to the public result context.

  confirm the high-precision reference assertion for `995340462.6258100` and both
  zero-side precision assertions fail:

```groovy
      BigDecimal x = pair[0]
      BigDecimal y = pair[1]
      BigDecimal expected = (x * x + y * y).sqrt(reference).round(MathContext.DECIMAL64)
      assertEquals(expected, x.hypot(y), "hypot(${x}, ${y}) should be correctly rounded")
```

1.2 [x] Replace the body of `hypot(BigDecimal, BigDecimal)` (`NumberExtension.groovy:695-711`)
  with the guard-precision form. This is the verified prototype — all seven probed
  cases match the 40-digit reference exactly:

```groovy
  static BigDecimal hypot(BigDecimal x, BigDecimal y) {
    BigDecimal ax = x.abs()
    BigDecimal ay = y.abs()
    if (ax == BigDecimal.ZERO) {
      return ay.round(RESULT_CONTEXT)
    }
    if (ay == BigDecimal.ZERO) {
      return ax.round(RESULT_CONTEXT)
    }
    BigDecimal larger = ax.max(ay)
    BigDecimal smaller = ax.min(ay)
    BigDecimal ratio = smaller.divide(larger, CALCULATION_CONTEXT)
    BigDecimal factor = BigDecimal.ONE
        .add(ratio.multiply(ratio, CALCULATION_CONTEXT), CALCULATION_CONTEXT)
        .sqrt(CALCULATION_CONTEXT)
    larger.multiply(factor, CALCULATION_CONTEXT).round(RESULT_CONTEXT)
  }
```

## 2. Round `toDegrees()` / `toRadians()` and use the high-precision π

`toDegrees(BigDecimal)` (`NumberExtension.groovy:946-948`) and `toRadians(BigDecimal)`
(`:976-978`) are the only two numeric methods that both (a) use the 17-digit public
`PI` constant rather than `CALCULATION_PI`, and (b) never round to `RESULT_CONTEXT`.

Groovy's `BigDecimal` division caps the result scale at `max(operandScales, 10)`,
so the output scale — and therefore the number of *noise* digits — is a function of
the caller's input scale:

```
toRadians(1.00000000000000000000000000G) => 0.017453292519943295555555555555555555555556
correct                                     0.017453292519943295769236907684886...
                                                              ^^^ from here on, noise

toDegrees(1G)                              => 57.2957795130823216               (scale 16)
toDegrees(1.000000000000000000000000000000G) => 57.2957795130823215782726544633670 (scale 31)
toDegrees(PI32)                            => 180.0000000000000022037471347786682
```

`testTranscendentalFunctionsUseDecimal64Precision` (`NumberExtensionTest.groovy:930`)

## 4. Make `ulp()` dispatch-proof (breaking)

`ulp` has four public overloads — `ulp(BigDecimal)` (`:471`), `ulp(Double)` (`:481`),
`ulp(Float)` (`:491`), `ulp(Number)` (`:503`). Extension-method *instance* dispatch
only considers overloads whose first parameter is assignable from the receiver, so
`(5).ulp()` correctly resolves to `ulp(Number)`. But a **direct static call** goes
through full Groovy method selection, where `Integer -> Float` is a legal coercion
and `Float` outranks `Number`:

```
NumberExtension.ulp(5 as Integer) => 4.76837158203125E-7   // == Math.ulp(5.0f)   WRONG
NumberExtension.ulp(5L)           => 4.76837158203125E-7   //                     WRONG
(5).ulp()                         => 1                     // correct
NumberExtension.ulp((Number) 5)   => 1                     // correct
```

Production code is safe because it is statically compiled, but **test sources in
this project compile dynamically by default**, and `testMinMaxSupportDirectDynamicStaticInvocation`
(`NumberExtensionTest.groovy:963-969`) establishes direct static invocation as a
supported call style. `release.md` records that the `min(Number, BigDecimal)` /
`max(Number, BigDecimal)` overloads were already removed in 0.4.0 for exactly this
"ambiguous dynamic static invocation" reason — `ulp` has the same defect and was missed.

`testUlpNumber` (`NumberExtensionTest.groovy:261-276`) already calls
`NumberExtension.ulp(intValue)` but only asserts `> 0`, which is why the bug is green
today.

**Approach:** collapse to a *single* public overload, `ulp(Number)`, so no selection
ambiguity is possible in any call style. The type-specific bodies become private
helpers with non-colliding names. Verified across 15 call-style × type combinations
(dynamic static, dynamic instance, `@CompileStatic` static, `@CompileStatic` instance)
— all correct.

```groovy

    BigDecimal expectedDoubleUlp = BigDecimal.valueOf(Math.ulp(1000.0d))
    BigDecimal expectedFloatUlp = BigDecimal.valueOf(Math.ulp(1000.0f) as double)

    assertEquals(1G, NumberExtension.ulp(5 as Integer), 'ulp(Integer) must be the decimal ulp')
    assertEquals(1G, NumberExtension.ulp(5L), 'ulp(Long) must be the decimal ulp')
    assertEquals(1G, NumberExtension.ulp((short) 5))
    assertEquals(1G, NumberExtension.ulp((byte) 5))
    assertEquals(1G, NumberExtension.ulp(5G))

    assertEquals(expectedDoubleUlp, NumberExtension.ulp(1000.0d))
```

4.2 [x] Replace the four overloads at `NumberExtension.groovy:471-509` with a single

```groovy
  /**
   * Returns the size of an ulp (unit in the last place) of this Number value.
   * <p>
   * Dispatch is by runtime type: {@code Double} and {@code Float} return their IEEE 754
   * ulp; every other Number type is treated as a decimal and returns 10<sup>-scale</sup>,
   * the positional value of its least significant digit.
   * <p>
   * This is deliberately the only public {@code ulp} overload. Additional typed overloads
   * make direct static invocation ambiguous under dynamic Groovy, which silently selected
   * the {@code Float} overload for {@code Integer} and {@code Long} arguments.
   *
   * @param self the Number value
   * @return a BigDecimal representing the size of an ulp
   */
  static BigDecimal ulp(Number self) {
    switch (self) {
      case Double -> floatingPointUlp((Double) self)
      case Float -> floatingPointUlp((Float) self)
      default -> decimalUlp(self as BigDecimal)
    }
  }

  /** Decimal ulp: 10<sup>-scale</sup>, the positional value of the least significant digit. */
  private static BigDecimal decimalUlp(BigDecimal self) {
    BigDecimal.ONE.scaleByPowerOfTen(-self.scale())
  }

  /** IEEE 754 ulp of a double value. */
  private static BigDecimal floatingPointUlp(Double self) {
    BigDecimal.valueOf(Math.ulp(self))
  }

  /** IEEE 754 ulp of a float value, widened to double. */
  private static BigDecimal floatingPointUlp(Float self) {
    BigDecimal.valueOf(Math.ulp(self) as double)
  }
```

## 6. Unify the exception type for domain violations (breaking)

The same class of error — an argument outside the function's domain — raises two
different exception types, so callers cannot write one catch:

```
log(-1)    -> IllegalArgumentException
log1p(-2)  -> IllegalArgumentException
sqrt(-1)   -> ArithmeticException
asin(2)    -> ArithmeticException
acos(2)    -> ArithmeticException
```

`ArithmeticException` does not extend `IllegalArgumentException`, so this is a real
break, not a widening. Standardize on `IllegalArgumentException`: the fault is the
argument, and it is the type the logarithm family already uses.

Note this is deliberately *not* applied to `exp`'s exponent guard (section 3) or to
the trigonometric range-reduction guard (`NumberExtension.groovy:740`) — those two
signal a computation limit of this implementation rather than a mathematical domain
violation, and `ArithmeticException` is correct for them.

6.1 [x] Guard negative inputs in `sqrt(BigDecimal)` before calling the JDK method and
  throw `IllegalArgumentException` with a message naming `sqrt` and the invalid value.
  Update the `sqrt(BigDecimal)` and `sqrt(Number)` `@throws` tags to document that
  type. This deliberately converts the JDK `ArithmeticException` into the uniform
  public domain-error contract.
6.2 [x] Change `asin(BigDecimal)` (`NumberExtension.groovy:1136-1138`) to throw
  `IllegalArgumentException`, keeping the message text identical.
6.3 [x] Change `acos(BigDecimal)` (`NumberExtension.groovy:1174-1176`) to throw
  `IllegalArgumentException`, keeping the message text identical.
6.4 [x] Update the `@throws` tags on `asin(BigDecimal)`, `asin(Number)`,
  `acos(BigDecimal)` and `acos(Number)`.
6.5 [x] Update the four assertions that pin the old inverse-trigonometric type. For
  `NumberExtensionTest.groovy:882`, `:885` (asin) and `:921`, `:924` (acos) —
  change `assertThrows(ArithmeticException)` to `assertThrows(IllegalArgumentException)`.
6.6 [x] Add a test asserting the contract is now uniform:


## 7. Give NaN and Infinity a defined contract

Every `Number` overload funnels through `self as BigDecimal`, which throws a JDK
exception naming neither the operation nor the receiver:

```
floor(Double.NaN)              -> NumberFormatException: Infinite or NaN
sqrt(Double.POSITIVE_INFINITY) -> NumberFormatException: Infinite or NaN
min(Double.NaN, 1)             -> NumberFormatException: Infinite or NaN
ulp(Double.NaN)                -> NumberFormatException: Character N is neither a decimal digit...
```

# Part C — Performance

## 8. Give `cbrt()` guard precision and drop the fixed iteration count

`cbrt(BigDecimal)` (`NumberExtension.groovy:641-663`) runs a fixed **8**
Newton-Raphson iterations entirely at DECIMAL64, with no guard digits. The seed is
`Math.cbrt(double)`, already accurate to ~16 digits, and Newton roughly doubles the
correct-digit count per step — so the iterations past the third do nothing except
re-round at the target precision.

Measured: 20k calls take **4745 ms**, versus 3104 ms for 20k `sqrt` calls.

Both problems have the same fix as section 1: compute at DECIMAL128, round once.
Verified prototype — **0 mismatches across 3015 values** (15 explicit cases spanning
`1e-40`..`1e300` plus a 3000-value sweep) against a 50-digit reference, at
**500 ms / 20k calls (9.5x faster)**.

> A convergence-based early exit at DECIMAL64 was tried first and rejected: it is
> fast but regresses `cbrt(0.7)` by 1 ulp (`0.8879040017426006` vs the correct
> `0.8879040017426007`). Do not reintroduce it — use the guard-precision form below.

8.1 [x] Add `private static final BigDecimal TWO = BigDecimal.valueOf(2)`,
  `private static final BigDecimal THREE = BigDecimal.valueOf(3)` and
  `private static final int CBRT_ITERATIONS = 3` to the constants block.
8.2 [x] Add the accuracy test. Run it first — `cbrt(0.7)` passes today, so this test
  is a regression guard for the rewrite rather than a currently-failing test:

```groovy

    MathContext reference = new MathContext(50)
    [2.0G, 7.0G, 1234.0G, 0.7G, 999999.0G, 1.0000001G, 27.0G,
     new BigDecimal('1e-40'), new BigDecimal('0.000001'), new BigDecimal('1e300'),
     new BigDecimal('123456789.987654321')].each { BigDecimal value ->
      BigDecimal expected = BigDecimal.valueOf(Math.cbrt(value.doubleValue()))
      30.times {

            .divide(BigDecimal.valueOf(3), reference)
      }

    }
  }
```

8.3 [x] Replace the body of `cbrt(BigDecimal)` (`NumberExtension.groovy:641-663`):

```groovy
  static BigDecimal cbrt(BigDecimal self) {
    if (self == BigDecimal.ZERO) {
      return BigDecimal.ZERO
    }
    BigDecimal absValue = self.abs()
    // Scale the value by powers of 1000 so its magnitude falls in double range,
    // compute the cube root, then scale back. This handles values far beyond
    // Double.MAX_VALUE or smaller than Double.MIN_NORMAL.
    int exponent = absValue.precision() - absValue.scale() - 1
    int k = Math.floorDiv(exponent, 3)
    BigDecimal scaled = absValue.movePointLeft(3 * k)
    // Seed from double-precision Math.cbrt (~16 correct digits), then refine with
    // Newton-Raphson: x_{n+1} = (2*x_n + a/x_n^2) / 3. Each step roughly doubles the
    // correct digit count, so three steps saturate DECIMAL128 guard precision.
    BigDecimal x = BigDecimal.valueOf(Math.cbrt(scaled.doubleValue()))
    for (int i = 0; i < CBRT_ITERATIONS; i++) {
      BigDecimal xSquared = x.multiply(x, CALCULATION_CONTEXT)
      x = x.multiply(TWO, CALCULATION_CONTEXT)
          .add(scaled.divide(xSquared, CALCULATION_CONTEXT), CALCULATION_CONTEXT)
          .divide(THREE, CALCULATION_CONTEXT)
    }
    BigDecimal root = x.movePointRight(k).round(RESULT_CONTEXT)
    self.signum() >= 0 ? root : root.negate()
  }
```

## 9. Short-circuit `log(value, base)` for base 10 and base 2

`log(BigDecimal, Number)` (`NumberExtension.groovy:266`) recomputes `lnSeries(base)`
on every call, even for bases 10 and 2 where `LN10` (`:88`) and `LN2` (`:86`) already
exist as 32-digit constants. Measured: 20k `log(x, 2)` calls take **15590 ms** versus
**7461 ms** for 20k `log10(x)` calls — 2.1x, entirely from the duplicated series.

This is a performance and DRY issue only, not a correctness one: `log10(x)` and
`log(x, 10)` were compared across 2..4000 with **zero** disagreements.

9.1 [x] Add a test asserting the short-circuit does not change any result:

```groovy
      assertEquals(value.log(), value.log(NumberExtension.E32), "log(${value}, e) should equal log(${value})")
    }
```

```groovy
    BigDecimal lnBase = switch (baseValue) {
      case BigDecimal.TEN -> LN10
      case TWO -> LN2
```

  **Do not reach for `equals` or `compareTo` here.** Groovy's `case` and `==` both use
  `compareTo` semantics for numbers, so they match scale-insensitively and even across
  numeric types — only `BigDecimal.equals` is scale-sensitive. Verified under static
  compilation (the mode this class is compiled in), with `TWO` as a `static final`
  field in the `case` label:

```
base 10, 10.0, 10.000  -> LN10       base 2, 2.0, 2.00 -> LN2       base 3, 7.5, 1 -> lnSeries
BigDecimal.TEN == 10.0G          : true    (both dynamic and @CompileStatic)
BigDecimal.TEN.equals(10.0G)     : false
BigDecimal.TEN == 10G            : true    (cross-type: BigInteger literal)
```

  An `equals`-based match would silently miss a caller passing `10.0G` and fall back
  to the slow path. The arrow switch is also the form AGENTS.md prescribes, and `==`
  is what the rest of this class already uses on BigDecimal (`self == BigDecimal.ONE`
  at `:163`, `ax == BigDecimal.ZERO` at `:697`).
