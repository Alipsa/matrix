# Matrix Core 3.10.0 Enhancement Candidates

This records the enhancement investigation and selection. Candidates 2–5 are
approved and incorporated as sections 9–12 of `3.10.0-plan.md`. That plan is the
authoritative implementation contract; the investigation below preserves the
original rationale. API examples describe planned methods, not existing APIs.

## 1. Named grouped aggregations — excluded

The proposed use case (multiple named aggregates from one column per group)
is already supported through GINQ expressions. A second API adds convenience
without a demonstrated need, so this candidate is excluded from the plan.

## 2. Join cardinality validation — approved, plan section 9

Evidence: `Joiner.doMerge` in `src/main/groovy/se/alipsa/matrix/core/Joiner.groovy`
emits all matching combinations, with no option to assert that a lookup table's
keys are unique. A duplicated department/customer key can silently multiply
rows even when a caller intended a many-to-one lookup.

Proposal: an optional typed cardinality argument, for example
`JoinCardinality.MANY_TO_ONE`, in a new merge overload. Preserve unrestricted
many-to-many behavior by default. Example:

```groovy
Joiner.merge(orders, customers, 'customerId', JoinType.LEFT,
    JoinCardinality.MANY_TO_ONE)
```

Contract to include if selected: ONE_TO_ONE checks both inputs, ONE_TO_MANY
checks left keys, MANY_TO_ONE checks right keys, MANY_TO_MANY imposes no
uniqueness constraint. Check uniqueness across each applicable whole input
before constructing output, using the join's existing normalized compound keys.
Exclude keys that cannot match (null/nonfinite) from the cardinality constraint.
Include offending keys and side in failures. Reject cardinality validation for
CROSS joins. Test composite keys, cross-runtime numeric equality, string/numeric
distinction, and duplicates with no matching rows. Reuse the join index logic.

## 3. Matrix integrity diagnostics — approved, plan section 10

Evidence: `Column` extends mutable ArrayList with descriptive `type` metadata;
callers can change values and lengths independently. `Matrix.rowCount()` uses
the first column's size. `Matrix.info()` reports counts and declared types but
does not identify ragged columns or incompatible cells. MatrixAssertions compares
two matrices rather than validating one matrix's integrity.

Proposal: a nonmutating `validate()` API returning structured issues with code,
column name/index, optional row index, expected type/length, and actual type/length.
Example: inspect `matrix.validate()` after import or direct column edits, before
SQL export or statistical processing.

Contract to include if selected: default checks for unequal column lengths and
duplicate/missing column names; opt-in declared-type checking, so legitimate
loose typing remains supported. Type checking treats null as allowed, primitive
types as wrappers, and null/Object declarations as unconstrained. Report issues
without converting values or throwing on the first bad cell. Do not claim to
detect stale index contents without an explicit index check. Reuse existing
type and comparison helpers; test deliberately corrupted matrices. Prefer this
bounded diagnostic addition over introducing a second strict Column hierarchy.

## 4. Core missing-value operations — approved, plan section 11

Evidence: core has Column `replaceNulls`/`removeNulls` and Matrix
`removeEmptyRows`, which removes entirely empty rows. Matrix-level `dropna` and
`fillna` already exist in `matrix-smile`'s `SmileFeatures.groovy`, despite their
basic tabular nature; SmileStats and SmileUtil direct callers to those methods.
This candidate relocates/reuses existing capability rather than inventing a
parallel implementation.

Proposal: core `withoutNullRows(List<String> columns)` and
`fillNulls(Map<String, ?> replacements)`, with documented convenience overloads.
Examples: `data.withoutNullRows(['price'])` and
`data.fillNulls([country: 'Unknown'])`.

Contract to include if selected: transformations return new matrices; no-argument
drop checks all columns and removes rows containing any null. Only null is
missing by default: blanks, NaN, and infinity remain unchanged. Reject unknown
columns, preserve names/order/index configuration, and retain schema for empty
results. Define replacement-type widening explicitly. Delegate matching Smile
methods to shared core logic only where their current semantics are identical;
keep adapters for differences and test both modules. Mean/median imputation and
broader missing-value policies are separate scope, not automatic additions.

## 5. Duplicate-row inspection and removal — approved, plan section 12

Evidence: core exposes Column `unique()` and ordinary Groovy collection methods,
but has no Matrix-specific duplicate-row API accepting a subset of key columns
while preserving the result as a Matrix with its schema and index configuration.
Grouping can be used as a workaround, but constructs submatrices for each group.

Proposal: `duplicated(List<String> columns)` returning a boolean mask and
`withoutDuplicateRows(List<String> columns)` returning a new Matrix. Example:
`events.withoutDuplicateRows(['source', 'eventId'])`.

Contract to include if selected: no-argument overloads use all columns; preserve
the first occurrence and input order by default; later equal rows are marked
true. Reject unknown or empty explicit selections. Null matches null; finite
numeric equality follows core normalized value semantics, so 1 and 1.0 compare
equally but '1' stays distinct. Define nonfinite and mutable-cell equality using
existing ValueComparison rules before implementation. Use normalized compound
keys without holding mutable Row objects as hash keys. Test schema/index
preservation, empty matrices, composite keys, and numeric precision.

## 6. Selection outcome

Candidates 2–5 are included in the release plan with API contracts, numbered
implementation tasks, regression tests, module verification, and documentation.
Candidate 1 is excluded. The selected copy-returning cleaning methods are named
withoutNullRows/withoutDuplicateRows to respect Matrix's in-place drop/remove
convention. Direct Column mutations remain a documented structural-version gap;
Matrix append paths are tracked. matrix-smile delegation requires core 3.10.0
and a matrix-smile 0.3.0 release with a published runtime core dependency.
Live reads, primitive column storage, and a strict typing
hierarchy remain outside the release scope.
