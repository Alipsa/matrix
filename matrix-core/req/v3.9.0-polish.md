# Matrix Core v3.9.0 Polish

## Verification status

The reported findings were checked against the current implementation, existing tests, and focused reproductions. The implementation, regression tests, documentation, release notes, and BOM/API expectations have now been updated in the working tree; no commit has been made.

`./gradlew :matrix-core:test --no-configuration-cache --rerun-tasks` passes with 567 tests, 0 failures. The full `./gradlew test --no-configuration-cache` regression suite also passes.

The following issues are confirmed:

- Missing column names can resolve through index `-1` to the last column in `type()`, the typed and untyped `getAt()` paths, `putAt(...)`, `rename(...)`, `apply(...)`, and `convert(...)`; `convert(Converter...)` can also silently ignore an unknown converter name. Both `columnIndex(...)` and `columnNames().indexOf(...)` are relevant sentinel sources. `columnIndexFuzzy` intentionally exposes the same `-1` sentinel, while `moveColumn(String,int)` and string-bearing `moveValue(...)` overloads are additional consumers that need explicit handling.
- `dropExcept(int...)` can leave active index metadata stale, causing silently wrong data: after `createIndex('k')` and `dropExcept(1)`, `lookup('a')` can return a one-row matrix from the stale `indexMap` instead of reaching `buildIndex`'s `IllegalStateException`.
- `Row.listIterator()` and `Row.subList()` can mutate the per-row copy without synchronizing the parent matrix, bypassing the `UnsupportedOperationException` guards on direct structural mutations.
- Row's default `List.replaceAll` and `List.sort` implementations currently mutate the per-row copy through the raw list iterator without synchronizing the parent matrix; `removeIf` is safe only because iterator removal is currently unsupported.
- Matrix construction through the `data(Map)`/`columns(Map)` builder path, `addColumn`/`addColumns`, and `upsertColumn` assignment paths can create ragged columns.
- Grid row mutators validate element types but not row width.
- Grid's live `getAt(int)`, `iterator()`, and publicly mutable `data` backing list bypass row-width validation; direct structural row or backing-data mutation can create ragged grids, while ordinary indexed value assignment is currently legitimate and must remain write-through.
- Both Grid list constructors retain the caller's outer list and row lists, so mutating the source after construction bypasses all Grid validation and can add rows or create ragged rows.
- Numeric summaries do not consistently filter null or non-numeric values before quartile and median calculations.
- The default tolerant `Matrix.equals()` conflicts with the exact-value `hashCode()` implementation.
- Comment-only CSV input can fail while extracting the header.
- Empty-string CSV input reports a clipboard-specific error message on the non-clipboard path.
- ResultSet imports use physical column names instead of alias-aware column labels.
- Rolling means round each value before accumulation, and the fixed-scale final divide cannot represent values below `1e-16` even after the raw sum is corrected.
- `addRows(List<List>)` validates and appends one row at a time, so a later invalid row leaves earlier rows appended after the call throws; `addRow(int,List)` also exposes a raw `ArrayList` bounds error for an invalid position.
- `removeRows(List<Integer>)` does not deduplicate repeated indexes and mutates columns before discovering out-of-range indexes, so it can silently remove the wrong rows or leave the matrix ragged after throwing.

The following behavior was checked and requires no change:

- `moveRow` and `moveColumn` already place a moved item at the requested destination in both directions. The removal is evaluated before `add`, so the destination is already a post-removal index. For example, `moveRow(0, 2)` produces `[1, 2, 0, 3, 4]`, and `moveColumn('a', 2)` produces `[b, c, a]`. Adjusting the destination for forward moves would regress this behavior.

## Implementation plan

### 1. Harden column lookup and index state

1.1 [x] Add a checked column-name resolution path and route all name-based consumer overloads through it, consistently rejecting missing names instead of allowing `-1` from either `columnIndex(...)` or `columnNames().indexOf(...)` to reach list indexing. Keep the low-level lookup APIs that document a `-1` result unchanged, but do not let their sentinel escape into mutation or indexing paths.

1.2 [x] Fix every consumer that uses a missing-name result as a list index or exposes an unclear sentinel error. This includes `type(String)`, `getAt(Integer,String)` (`m[0, 'zzz']` currently returns the last column's value), `getAt(int,String,Class)` and its four-argument default-value overload, `moveColumn(String,int)`, `putAt(Number,String,Object)` (a typo currently writes into the last column), `rename(String,String)` (a typo currently renames the last column), and all string-bearing `moveValue` overloads (`String,String`, `int,String`, and `String,int`). Also fix the `columnNames().indexOf(...)` consumers `apply(String,Closure<Boolean>,Closure)` (a typo rewrites the last column's values), `convert(String,Class,Closure)` (a typo rewrites the last column's values and declared type), and `convert(Converter...)` (an unknown converter column name is silently ignored). Add the missing-name check to `apply(String,List<Integer>,Closure)` so it reports the same clear `IllegalArgumentException` as `apply(String,Closure)` instead of delegating `-1` to the integer overload. Leave `columnIndex(String)`, `columnIndexFuzzy(String)`, and `columnIndices(...)` returning `-1` as documented; their callers must handle that sentinel explicitly. Do not change the already-guarded `apply(String,Closure)` overload, `column(String)`, `drop(String...)`, `dropExcept(String...)`, `orderBy(String,Boolean)`, or `orderBy(Map)` paths; preserve the existing `drop(String...)` validation that checks for `-1`.

1.3 [x] Update `dropExcept(int...)` to reset the index when an indexed column is removed and invalidate it whenever the remaining index state may no longer be trusted, preventing stale-index lookups from returning wrong rows.

1.4 [x] Add regression tests for missing column names and indexed matrices after integer-based column selection.

### 2. Preserve rectangular data invariants

2.1 [x] Validate that all Matrix columns have the same length in the `data(Map)`/`columns(Map)` builder path and constructors. `rows()` already validates row widths (for example, `Row 1 has 1 elements but expected 2`); the missing builder case allows `data(a: [1, 2, 3], b: [4])` to produce `rowCount() == 3` with column sizes `[3, 1]`, and `row(2)` to return `[3, null]`.

2.2 [x] Apply the same validation to every `addColumn`, `addColumns`, `upsertColumn`, and `and(Map)` path, including matrices with a schema but zero rows. Use `columnCount()` as the discriminator: when `columnCount() == 0`, the added non-null column establishes the matrix width and any size is valid; when `columnCount() > 0`, the new or replaced column must match the established width of the existing columns, which is `0` for a schema-only matrix, regardless of `rowCount()`. Do not remove the zero-column construction path or make the first column compare against `rowCount()`. `and(Map)` must validate in two passes before mutating: determine the target width from the existing schema or the map's non-null lists, reject conflicting non-null sizes up front, then expand null entries to that target width before delegating to `addColumn`. Thus `and([a: null])` remains equivalent to `addColumn('a', Object)`, and `and([a: null, b: [1, 2, 3]])` succeeds at width 3 regardless of map order. Cover all public upsert entry points: `putAt(String,List)` (`m['a'] = [...]`), `putAt(Integer,List)` (`m[0] = [...]`), and `setProperty` (`m.a = [...]`). The typed assignment form `putAt(String,Class,Integer,List)` must reject the same mismatched sizes as the untyped form, so `m['x', Integer] = [...]` and `m['x'] = [...]` have consistent validation.

2.3 [x] Make Grid row validation enforce the established width for `add`, `addAll`, `leftShift`, indexed insertion, replacement, and row assignment. Copy the outer list and every row in both `Grid(List<List<T>>)` and `Grid(List<List<T>>, Class<T>)`, making construction a snapshot rather than an alias of caller-owned lists. Close the direct structural-mutation escape hatches while preserving live value writes: `getAt(int)` and `iterator()` must return checked live row views whose `set(int,T)` writes through to the backing row, while `add`, `remove`, `clear`, `addAll`, and other structural operations throw `UnsupportedOperationException`; the iterator itself must not support removal. Preserve the public `data` API as a read-only outer view of the same checked live row views, so existing read-only consumers and `data.size()` API coverage continue to work, while outer-list and inner-row structural mutations and direct reassignment are rejected. Document that indexed row values remain write-through but width-changing access must go through validated Grid methods.

2.4 [x] Define and test behavior for adding the first row to an empty Grid and for empty/schema-only matrices. Explicitly test that adding the first column to a zero-column matrix establishes its width and accepts its values, while adding or upserting a non-matching column into a schema-only matrix is rejected. Test `and(Map)` with null-list entries on both established-width and zero-column matrices, including order-independent success of `and([a: null, b: [1, 2, 3]])` at width 3 and equivalence of `and([a: null])` to `addColumn('a', Object)`, while conflicting non-null list sizes are rejected before any mutation. Cover matching rejection of mismatched typed and untyped upsert assignments, including `m['a'] = [...]`, `m[0] = [...]`, and `m.a = [...]`. Test `leftShift` alongside the other validated row writers; verify that `g[0][1] = value`, iterator row `set`, and `grid.data[0][1] = value` remain write-through, while row/data `add`, `remove`, `clear`, `addAll`, outer-list mutation, iterator removal, and direct data reassignment fail without changing width. Also verify that mutating the source outer list or any source row after either constructor returns does not affect the Grid.

### 3. Make Row views safe

3.1 [x] Restore the Row invariant after every supported mutation: `size() == columnNames().size()`, and value changes write through to the parent matrix. Make both `listIterator().set(...)` and `listIterator(int).set(...)` parent-aware so `replaceAll` performs write-through value updates. Make `sort(Comparator)` throw `UnsupportedOperationException`, because sorting would move values across columns and can violate their declared types; do not implement it as a write-through permutation. Keep `listIterator().add(...)`/`listIterator(int).add(...)` and `listIterator().remove()`/`listIterator(int).remove()` throwing `UnsupportedOperationException` like the direct Row methods. Also make `minusColumn(String)` validate the name before removal, matching the existing error behavior of the other name-based Row accessors instead of allowing `columnNames.indexOf(...) == -1` to reach `remove(-1)`.

3.2 [x] Correct `Row.subList()` semantics and GroovyDoc. The `(int, int)` overload currently returns a live `content.subList` view; the other three overloads return copies. Preserve or deliberately revise those semantics, but ensure value mutation is parent-aware and structural mutation cannot break the row/column invariant. Do not document the `(int, int)` overload as a disconnected list unless it is changed to return a copy.

3.3 [x] Ensure both iterator escape hatches (`listIterator()` and `listIterator(int)`) and all sublist changes cannot silently bypass Matrix index invalidation or row/column invariants, including `set`, `add`, `remove`, and structural sublist operations. Preserve iterator removal rejection, including the iterator used by `removeIf`, so `removeIf` cannot become a partial-mutation path while replacing the current unmodifiable iterator with checked views.

3.4 [x] Add tests covering iterator `set`, iterator add/remove, `replaceAll` write-through updates, `sort` rejection, `removeIf` rejection without partial mutation, sublist value replacement, and sublist structural mutation, including the documented live-view versus copy behavior of each overload.

### 4. Validate row and column movement inputs

4.1 [x] Make `moveColumn(String,int)` reject an unknown column name with a clear error instead of allowing `mColumns.remove(-1)` to throw `IndexOutOfBoundsException`.

4.2 [x] Validate all row and column source and destination bounds before the first mutation, and define same-index behavior as a no-op. In particular, `moveRow` must not validate inside its column iteration, because a late out-of-range failure can leave the matrix ragged after earlier columns have moved. Apply the same validate-before-mutate rule to `addRows(List<List>)`: validate every row's width before appending any row, so a later invalid row cannot leave the matrix partially updated. Add an explicit position check to `addRow(int,List)` and report the valid row range and current row count instead of leaking the underlying `ArrayList` bounds exception. Extend the prevalidation to `removeRows(List<Integer>)` and `removeRows(int...)`, validating the complete index set before touching any column; deduplicate sorted indexes before applying shift compensation so repeated indexes remove each requested row only once. `removeEmptyRows()` already supplies distinct ascending indexes and needs no change.

4.3 [x] Add tests for unknown column names, invalid source and destination indices, same-index moves, and valid moves in both directions; verify the resulting order and index state. Also test that `addRows` is atomic when a later row has the wrong width, invalid `addRow` positions fail with a clear row-bounds error without mutation, duplicate `removeRows` indexes remove only the distinct requested rows, and an out-of-range `removeRows` index leaves every column unchanged and rectangular.

### 5. Correct statistical summary behavior

5.1 [x] Filter null and non-numeric values in the median and quartile/IQR paths, bringing the two outlier methods in line with the other numeric aggregates. The primary defect is silently wrong values: `Stat.median([1, null, 3])` currently returns `1` because Groovy sorts null first; the correct median is `2`. `Stat.summary` likewise reports `Median: 1` and `1st Q: 1` without an error. The other six aggregate paths (`mean`, `sd`, `variance`, `sum`, `min`, and `max`) already handle this input correctly, so the fix is targeted rather than a broad null-handling change.

5.2 [x] Define the result for empty and all-null numeric columns, ensuring summaries do not fail in quartile or median calculation. The current secondary failures are `NullPointerException` for all-null data and `IllegalArgumentException` from quartiles for an empty column.

5.3 [x] Add regression tests for mixed numeric/null values, all-null numeric values, empty columns, and direct `median`, `quartiles`, and `iqr` calls. Include `quartiles([1, 2, 3, 4]) == [2, 3]` with `iqr == 1`, and `quartiles([1, null, 2, 3, 4]) == [2, 3]` with `iqr == 1`, proving that a null cannot shift Q1 to `1` or double the IQR to `2`.

### 6. Define equality and hashing semantics

6.1 [x] Remove the no-argument `Matrix.equals()` `allowedDiff = 0.0001` tolerance. With `allowedDiff = 0`, numeric comparison remains `BigDecimal.compareTo`-style, while `hashCode()` remains scale-sensitive through `Column`'s content-based `ArrayList` hash. This removes the tolerance-induced violation, but scale/boxing cases such as `1.0G` versus `1.00G` (or `1` versus `1.0G` in compatible Number/Object columns) can still compare equal while hashing differently; accept and document that remaining limitation unless hash normalization is explicitly added.

6.2 [x] Keep the existing tolerance-based API unchanged: `MatrixAssertions` and the 7-argument `equals` overload remain the supported mechanisms for approximate comparison.

6.3 [x] Sweep all cross-module matrix comparison call sites before the full regression suite. Changing default equality affects decimal comparisons across the repository. Inventory relevant `assertEquals` call sites, migrate approximate comparisons to `MatrixAssertions`, and preserve exact comparisons intentionally, so the full suite is not the first discovery mechanism.

6.4 [x] Add tests for tolerance removal, near-equal numeric matrices, unequal matrices, and the documented scale/boxing hash limitation. Do not assert a universal `equals`/`hashCode` contract unless hash normalization is added.

### 7. Fix precision and input adapter issues

7.1 [x] Define and implement the rolling-mean output contract: compute the mean from the already-full-precision `rawSum` and remove the `scaledSum` accumulator, including its `setScale` calls in `addValue` and `removeValue`. Replace the fixed-scale `divide(count, MEAN_SCALE, HALF_UP)` with a documented 16-significant-digit `MathContext` (so values such as `5E-17` remain representable); this is an intentional public output-scale change. Delete the `if (scaledSum == 0)` early return rather than migrating it: `numericCount == 0` already returns `null` before division, so the guard is not needed to prevent division by zero, and a fixed-scale zero contradicts the new contract.

7.2 [x] Add rolling-mean regression tests for the new output contract, including `[5E-17] x4` yielding `5E-17`, an all-zeros input yielding numeric zero without a forced scale-16 representation, and a mixed-value case that distinguishes raw accumulation from per-addend rounding, such as `[0.12345678901234564, 0.12345678901234565]` (raw mean rounds to `0.1234567890123456`, while rounded addends produce `0.1234567890123457`). Do not use `[0.33333333333333335] x3` as the regression case because raw accumulation and per-addend rounding produce the same result there.

7.3 [x] Define comment-only CSV behavior for both header modes. With `firstRowAsHeader: false`, use `# types:` as the only directive that can establish schema width when there are no data rows, generate forward names (`[c1, c2, ...]`), and retain the parsed matrix name/directives; `# index:` names indexed columns but does not establish the column set or width. If no `# types:` directive establishes a width, the result has zero columns. If a headerless `# index:` directive names columns that are absent from the generated schema, reject it with a clear `IllegalArgumentException` naming the unavailable index column rather than silently ignoring the directive. With `firstRowAsHeader: true` and no data row available to supply a header, throw a clear `IllegalArgumentException` explaining that the header row is missing rather than an opaque `IndexOutOfBoundsException`. Keep the empty-input messages context-dependent: `csvString(String, Map)` reports empty CSV content, while `clipboard(Map)` preserves an empty-clipboard message, using a clipboard-specific check or rewrap before/around delegation.

7.4 [x] Add CSV regression tests covering all behaviors in 7.3: comment-only input with `firstRowAsHeader: false` and `# name: demo`/`# types: Integer, String` yields an empty matrix with `name == 'demo'`, `types == [Integer, String]`, and `columnNames() == [c1, c2]`; a headerless `# index: id` directive with no generated `id` column fails with the specified clear missing-index-column `IllegalArgumentException`; comment-only input with `firstRowAsHeader: true` fails with the specified clear missing-header `IllegalArgumentException`; and `csvString('')` rejects with the direct empty-CSV-content message. Do not test `clipboard(Map)` by reading the system clipboard in this deterministic CSV regression task; its context-specific empty-clipboard message belongs to the implementation and GroovyDoc checks.

7.5 [x] In `MatrixBuilder.data(ResultSet)`, change `rsmd.getColumnName(i)` to `rsmd.getColumnLabel(i)` so SQL aliases become matrix column names.

7.6 [x] Add a ResultSet metadata test proving that SQL aliases are preserved through `getColumnLabel()`.
