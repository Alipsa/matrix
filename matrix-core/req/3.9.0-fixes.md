# Part A — Critical

## 1. `Matrix` constructor drops columns when padding

`Matrix.groovy:307-312`

```groovy
if (dataTypes.size() > columns.size()) {
  int dataRowCount = columns.isEmpty() ? 0 : columns[0].size()
  for (int i = 0; i < dataTypes.size() - columns.size(); i++) {   // bound re-evaluated as columns grows
    columns.add(new ArrayList(Collections.nCopies(dataRowCount, null)))
  }
}
```

The loop bound is re-evaluated each iteration while the body grows `columns`, so only
about half the missing columns are added. Nothing catches it: `sanitizeTypes` uses
`dataTypes` (correct size), so `mHeaders.size() == mTypes.size()` passes and headers are
silently dropped. Verified: `new Matrix('t', ['a','b','c','d','e'], [], [String]*5).columnCount()`
returns **3**, expected 5.

Reachable from `MatrixBuilder.data(ResultSet)` — that path ends in
`columns(rows.transpose())` (`MatrixBuilder.groovy:996`), i.e. `columns([])`, landing in
the buggy loop, so **an empty JDBC result set produces a Matrix with the wrong number of
columns**. Note: the `rows([])` path is *not* affected (`MatrixBuilder.groovy:249-251`
returns early without touching `columns`, so the constructor's null-branch pads correctly);
only an explicit empty-but-non-null column list triggers the bug.

1.1 [x] Hoist the loop bound in `Matrix.groovy:309`: compute `int missing = dataTypes.size() - columns.size()` before the loop and iterate `i < missing`
1.2 [x] Stop mutating the caller-supplied list: copy `columns` into a new `ArrayList` before padding
1.3 [x] Add a test asserting `new Matrix(name, 5 headers, [], 5 types).columnCount() == 5` and that headers are all preserved
1.4 [x] Add a test for `MatrixBuilder.data(ResultSet)` with an empty result set preserving column count
1.5 [x] Sanity-test the `rows([])` path still pads to the declared column count (currently correct, guard against regression)

**Files:** `matrix-core/src/main/groovy/se/alipsa/matrix/core/Matrix.groovy`
**Tests:** `./gradlew :matrix-core:test --tests 'MatrixTest' --tests 'MatrixBuilderTest'`

## 2. `Stat.frequency(Matrix, groupName, columnName)` produces a wrong cross-tab

`Stat.groovy:913-925`

Each group's frequency table is sorted independently
(`orderBy(Frequency: DESC, Value: ASC)` at `Stat.groovy:879`), `tbl[columnName]` is
overwritten per group, so only the **last** group's `Value` ordering survives as row
labels and every group's `Frequency` column is paired against it positionally.
Verified with mtcars-like data: column `'4'` comes out `[10, 2]` but must be `[2, 10]`
per the doc comment at `Stat.groovy:896-904` (R's `table(vs, gear)`); the other gear
columns are accidentally correct only because their sorted order happens to match the
last group's.

With unequal distinct-value counts per group it throws instead:
`Matrix.builder().data(tbl)` → `IllegalArgumentException: Column 'a' has 2 rows but
previous columns have 1 rows`.

`StatTest.testFrequencyTable` (`StatTest.groovy:192-206`) currently asserts the incorrect
`[10, 2]` for the gear-4 column and must be corrected as part of the fix.

2.1 [x] Compute each group's frequency as a value→count map; build the union of category values across all groups in a stable order (first-appearance order is fine — document the choice)
2.2 [x] Emit each group's column by looking counts up by value from the union, defaulting to 0 — never positional alignment
2.3 [x] Correct the gear-4 expectation in `StatTest.testFrequencyTable` to `[2, 10]`. Note: this expectation assumes first-appearance order `[0, 1]` for the `vs` labels; if a different ordering is chosen in 2.1, the gear-3/gear-5 assertions move with it — set all column expectations to match the implemented ordering
2.4 [x] Add a test with groups that have different distinct-value sets and counts (asserts no throw and correct 0-fill)

**Files:** `matrix-core/src/main/groovy/se/alipsa/matrix/core/Stat.groovy`
**Tests:** `./gradlew :matrix-core:test --tests 'StatTest'`

## 3. `ValueConverter.convert(x, Boolean)` returns Groovy truthiness

`ValueConverter.groovy:70-95`

The switch has no `Boolean`/`boolean` case, so conversion falls through to
`default -> type.cast(o)` → `ClassCastException` → `o.asType(Boolean)`, which is Groovy
truth (any non-empty String is `true`). Verified:

```groovy
convert('false', Boolean)   // => true   (wrong)
convert('0', Boolean)       // => true   (wrong)
ValueConverter.asBoolean('false')   // => false  (the intended semantics, ValueConverter.groovy:195-214)
```

Silent data corruption on any String → Boolean column conversion. Also verified: the
primitive `float` case is missing (`convert('1.5', float)` throws `GroovyCastException`
while wrapper `Float` works).

3.1 [x] Add `case Boolean, boolean ->` to the `convert` switch, wiring to the existing `asBoolean(Object)` semantics
3.2 [x] Add the missing primitive `float` case alongside the existing `Float` case (wire to `asFloat`)
3.3 [x] Pin the `Character` semantics deliberately: current behavior converts single-char Strings (`convert('a', Character)` → `'a'`) and throws `GroovyCastException` for multi-char Strings — keep exactly that (do **not** add first-char truncation; that would be new silent data loss). Add an explicit `case Character, char` delegating to the same path for readability, and tests pinning both the single-char and multi-char behaviors
3.4 [x] Add tests for `convert('false', Boolean)`, `convert('no', Boolean)`, `convert('yes', Boolean)`, `convert('0', Boolean)`
3.5 [x] Add a `Matrix.convert(columnName, Boolean)` round-trip test on a String column
3.6 [x] Add a test for `convert('1.5', float)`

**Files:** `matrix-core/src/main/groovy/se/alipsa/matrix/core/ValueConverter.groovy`

## 4. `Stat.means(Matrix, List<String>)` accumulates in `double`

`Stat.groovy:428-445` — `sum += value` with an `Object`-typed closure parameter
accumulates in double, then divides an unscaled `BigDecimal`, so the "optimized columnar"
path disagrees with every other mean API. Verified exactly:

```groovy
d = [1.1d, 2.2d]
Stat.means(m, ['d'])       // => [1.65000000000000015]
Stat.mean(m.column('d'))   // => 1.6500000000000000
```

The sibling overload `means(List<List<?>>, List<Integer>)` (`Stat.groovy:405-426`)
already accumulates correctly (`value as BigDecimal`); `mean(List<?>)`
(`Stat.groovy:492-511`) divides with scale 16, `RoundingMode.HALF_UP`.

4.1 [x] Accumulate via `ValueConverter.asBigDecimal(value as Number)` (skip nulls) to match the sibling overload
4.2 [x] Divide with the same scale/rounding as `Stat.mean` (scale 16, `RoundingMode.HALF_UP`)
4.3 [x] Add a test asserting `Stat.means(m, ['d']) == [Stat.mean(m.column('d'))]` for a Double column, and for a mixed-type column

**Files:** `matrix-core/src/main/groovy/se/alipsa/matrix/core/Stat.groovy`

## 5. `Joiner` key lookup is type-strict — Integer/Long keys silently join to nothing

`Joiner.groovy:259,264-265,270-274,174` — the join index is a `LinkedHashMap` keyed on
`List<Object>` of raw cell values, so `List.equals` element comparison applies and
numerically equal keys of different runtime types never match. Verified:
`Joiner.merge(x, y, 'id', JoinType.INNER)` with `id` Integer `[1,2]` vs Long `[1L,2L]`
returns **0 rows, no error or warning**; same-type returns 2.

`ValueComparison` already provides numeric-tolerant equality
(`util/ValueComparison.groovy:29`, compares Numbers by `toBigDecimal()`), used in
`Matrix.equals` via `checkValues` (`Matrix.groovy:1922`); joins should be consistent
with it. Caveat: its existing helpers do not solve this directly — `valuesAreDifferent`
is a pairwise predicate and `normalizedValueHash` returns only an `int`; neither yields a
canonical key object for the join's `Map<List<Object>, …>`.

5.1 [x] Add a public `ValueComparison.normalizeKey(Object)` returning `value.toBigDecimal().stripTrailingZeros()` for finite `Number` and the value itself otherwise — `stripTrailingZeros()` is required or `1.0` and `1.00` still miss each other. Guard non-finite values: `toBigDecimal()` throws `NumberFormatException` on NaN/infinity (verified), so return the raw value for those and let the key decision in 5.3 cover them
5.2 [x] Apply `normalizeKey` to both index construction (`Joiner.groovy:264-265,270-274`) and probe keys, so numerically equal keys of different runtime types hash and compare equal
5.3 [x] Decide and document key semantics in the `Joiner` class javadoc: null keys (recommend: never match, matching SQL), NaN/infinite keys (same recommendation, since normalizeKey leaves them raw), and String-vs-numeric behavior (recommend: no cross-type match for String keys)
5.4 [x] Add tests joining Integer↔Long, Integer↔BigDecimal (must match), and Integer↔String keys (must not silently match — pin the documented behavior)

**Files:** `matrix-core/src/main/groovy/se/alipsa/matrix/core/Joiner.groovy`, `matrix-core/src/main/groovy/se/alipsa/matrix/core/util/ValueComparison.groovy`
**Tests:** `./gradlew :matrix-core:test --tests 'JoinerTest'`

## D.2 Column

D.2.1 [x] `Column.applyListOp` (`Column.groovy:178-186`) silently ignores extra elements of a longer operand — verified: `new Column('a',[1,2]) + [10,20,30] == [11,22]`. The truncation happens in `applyListOp` (it iterates over `this`, indexing into the operand); the null-padding of a *shorter* operand lives in `fill` (`Column.groovy:268-276`) and is deliberate — keep it. Decision: throw `IllegalArgumentException` only when the operand is longer than the column (silent truncation is data loss); shorter operands keep null-padding. **Behavior break in a minor release, and existing tests pin the truncation in all five list operators:** update the longer-operand assertions in `testPlusList` (`ColumnTest.groovy:19,27`), `testMinusList` (`:56,64`), `testMultiplyList` (`:93,101`), `testDivList` (`:120,128`) and `testPowerList` (`:149,157`) to assert the exception instead — ten assertions in total. The shorter-operand padding assertions in all five methods still pass unchanged, and no other module exercises Column list arithmetic (grepped).
D.2.2 [x] `Column.subList(IntRange)` (`Column.groovy:278-280`) uses `range.min()/max()`, so a reverse range like `3..1` silently returns ascending order (verified: `[10,20,30,40,50].subList(3..1) == [20,30,40]`); it also returns an `ArrayList` live view rather than a `Column`. Reject reverse ranges with a clear exception and return a `Column`.
D.2.3 [x] `Column(String name, Collection c)` (`Column.groovy:54-57`) leaves `type` as `null`, unlike every sibling constructor (which default to `Object`). Set `type = Object`.

## D.3 Stat

D.3.1 [x] Both `Stat.sum(List)` (`Stat.groovy:117-125`) and `Stat.sum(List, Class)` (`:127-135`) throw `NumberFormatException` on non-finite doubles — verified by execution for NaN and positive infinity on both overloads (`Character N/I is neither a decimal digit...`). ## D.4 ValueConverter

D.4.1 [x] `ValueConverter.asInteger`/`asByte`/`asShort` throw `NumberFormatException` on text containing numeric junk (verified: `asInteger('1.2.3')` throws while `asBigDecimal('1.2.3')` returns `null`; purely non-numeric text returns null in both). Align with the `asBigDecimal` contract: return `null` for unparseable input.
D.4.2 [x] `ValueConverter.isNumeric` (`:445-462`) uses `NumberFormat.getInstance()` with the default locale, making the predicate locale-dependent. Verified by execution: `isNumeric('1.5')` is **true** under `de_DE` (`.` is a grouping separator there, so the parse consumes the whole string) but **false** under `sv_SE` or `fr_FR` (where `,` is the decimal separator and `.` is not a separator at all). Worse than a wrong boolean under `de_DE`: `1.5` parses to `15`, so any caller reusing the same format to convert gets a wrong value. Low practical impact — the only consumer is `asDate(Object)` compact-date parsing (`ValueConverter.groovy:607`, confirmed by grep), which is digit-only in practice. Parse with a `Locale.ROOT` format or make the locale dependence explicit in the javadoc.
D.4.3 [x] `ValueConverter.fixNegationFormat` (`:744-750`) casts unconditionally to `DecimalFormat`; a caller-supplied non-`DecimalFormat` `NumberFormat` throws `ClassCastException` (latent — JDK `getInstance()` returns `DecimalFormat`). Guard with `instanceof` and no-op for other formats.
