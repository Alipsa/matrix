## 1. `MatrixResultSet.deleteRow()` desyncs the cursor from the underlying data

`deleteRow()` calls `matrix.removeRows(rowIdx)`, which physically removes the row and shifts every following row left by one (`Matrix.removeRows` uses list-remove semantics). `rowIdx` is never adjusted, so the row that slides into the just-vacated index is silently skipped by the next `next()` call. `deleteRow()` also skips the `ensureCurrentRow()` guard that every other row-data method uses, so calling it before `next()`/after `afterLast()` throws a raw `IndexOutOfBoundsException` from `Matrix.removeRows` instead of a `SQLException`.

1.1 [x] Add a failing regression test in `matrix-sql/src/test/groovy/MatrixResultSetTest.groovy`, e.g. `testDeleteRowDoesNotSkipTheFollowingRow`:
    - Build a 4-row source Matrix (`id: [1,2,3,4]`) and keep a reference to it (`Matrix source = ...`).
    - **`MatrixResultSet` clones its constructor argument** (`MatrixResultSet.groovy:74`, `this.matrix = matrix.clone()`) — the `ResultSet` never mutates `source`. Assert against the result set's own data, not `source`: use `rs.unwrap(Matrix)` (confirmed to return the live internal clone, `MatrixResultSet.groovy` `unwrap()`), e.g. `Matrix rsData = rs.unwrap(Matrix)`.
    - `rs.absolute(2)` (cursor on row id=2), call `rs.deleteRow()`.
    - Assert `rsData.rowCount() == 3` and `getInt(1)` for the current row is `3` (the row that slid into the deleted position is still the *current* row, not skipped).
    - Explicitly assert `source.rowCount() == 4` (the original Matrix passed to the constructor is untouched).
    - Assert `rs.next()` then moves to id=`4` (not skipping past it).
    - Add a second case: delete the *last* row (`rs.absolute(-1)` then `deleteRow()`) and assert `rs.next()` returns `false` (cursor correctly lands after-last, not out of bounds).
    - Add a guard case: `rs.beforeFirst(); assertThrows(SQLException) { rs.deleteRow() }` (was previously an `IndexOutOfBoundsException`).
    - Run: `./gradlew :matrix-sql:test --tests "MatrixResultSetTest" --rerun-tasks` and confirm the new assertions fail against the current implementation before fixing it.

## 2. Calendar-aware temporal getters: pin down the contract, then fix or document it

`getDate/getTime/getTimestamp(int|String, Calendar)` only apply the supplied `Calendar` when the underlying Matrix cell is a raw `Number` (epoch millis); for a cell already holding a `java.sql.Date`/`Time`/`Timestamp`/`String`, the fallback branch calls the exact same conversion as the no-`Calendar` overload, so `cal` has no effect.

**This needs a decision before coding a fix**, because existing tests (`MatrixResultSetTest.testTemporalLabelAndCalendarGettersUpdateWasNull`, `testCalendarGettersConvertStringStoredTemporalValues`) currently assert *identity* behavior (calendar has no visible effect) for `Date`/`Time`/`Timestamp`/`String`-typed columns, while `testCalendarGettersWithNumberMillisAppliesTimezoneOffset` asserts the calendar *does* shift the result for `Number`/millis-typed columns. It is plausible this asymmetry is intentional (an already-typed `java.sql.Date`/`Timestamp` is an unambiguous instant; a raw millis `Number` is not, per the JDBC javadoc: "uses the given calendar... if the underlying database does not store timezone information"). Do not silently change this contract — confirm it with the user first.

2.1 [x] Investigate and confirm with the user (see `AskUserQuestion` if genuinely blocked, otherwise state the recommendation and proceed): should `getDate/getTime/getTimestamp(_, Calendar)` reinterpret the wall-clock fields of an already-typed `Date`/`Time`/`Timestamp`/`String` cell in the supplied calendar's zone (matching real-world JDBC driver behavior for zoneless `DATE`/`TIME`/`TIMESTAMP` columns), or is "calendar only affects raw millis `Number` cells" the intended, permanent contract for this in-memory result set?
    - **If "reinterpret" is chosen, this decision must also cover `ZonedDateTime` cells for `getTimestamp(_, Calendar)`** (the only affected getter — `asSqlDate`/`asSqlTime` don't accept `ZonedDateTime`; `asTimestamp` does). Unlike every other cell type this task reinterprets (`Number`, `Date`/`Time`/`Timestamp`, `LocalDate`/`LocalTime`/`LocalDateTime`, `String`), a `ZonedDateTime` is the one type that already carries a genuine, unambiguous zone of its own, so "reinterpret in `cal`'s zone" is ambiguous between two different operations:
      - **(a) Discard the embedded zone and reinterpret its local fields in `cal`'s zone** — i.e. treat it exactly like a `LocalDateTime` cell (`val.toLocalDateTime()`, then the same `atZone(cal.timeZone.toZoneId())` construction as every other reinterpreted type).
      - **(b) Preserve the actual instant and convert it into `cal`'s zone** — i.e. `val.withZoneSameInstant(cal.timeZone.toZoneId())`, changing only the zone label while keeping the same point in time.
      - **Recommendation: (a).** The no-`Calendar` `getTimestamp(int)` path (`ValueConverter.asTimestamp`) already discards the embedded zone for a `ZonedDateTime` cell (`Timestamp.valueOf(o.toLocalDateTime())`, confirmed at `ValueConverter.groovy:660-662`) — it never treats the cell as an unambiguous instant even today. Option (a) keeps `getTimestamp(_, Calendar)` internally consistent with every other reinterpreted cell type in this task (all "reinterpret wall-clock fields in the target zone," none "convert a known instant between zones") and with its own no-`Calendar` sibling's treatment of the same cell type. Option (b) would make `ZonedDateTime` the only cell type in the whole method where the `Calendar` overload's result isn't reachable from the no-`Calendar` result via a pure zone-reinterpretation, which would be a surprising, undocumented special case. Proceed with (a) unless the user overrides.

2.2 [x] If the answer is "reinterpret it": extend `getDate/getTime/getTimestamp(int, Calendar)` in `MatrixResultSet.groovy` (~lines 2893, 2949, 3005) with a source-zone policy that is well-defined and provably independent of the JVM default timezone at call time. **`toLocalDate()`/`toLocalTime()`/`toLocalDateTime()` on `java.sql.Date`/`Time`/`Timestamp` are NOT zone-agnostic** — they're implemented via the legacy `java.util.Date` accessors (`getYear()`/`getMonth()`/`getDate()`/`getHours()`/...), which decode the object's internal epoch-millis value using `TimeZone.getDefault()` at the moment they're called. Using them here would reintroduce exactly the ambient-JVM-default dependency this task is meant to eliminate — a `java.sql.*` object carries only an absolute instant (epoch millis) with no embedded zone, so there is no way to recover an "original zoneless wall-clock value" from one without separate source-zone metadata, which this class does not have. Adopt this policy instead:
    - **`Number` cells (unchanged):** already correct — `calendarDateMillis`/`calendarTimeMillis`/`calendarTimestampMillis(millis, cal)` treat the raw millis as a UTC-sourced wall clock and reinterpret it in the target calendar's zone.
    - **`java.util.Date`/`java.sql.Date`/`Time`/`Timestamp` cells:** these are *also* just epoch millis under the hood (`val.getTime()` is a plain epoch-millis number — unlike `toLocalDate()` etc., it does **not** go through any default-zone-dependent accessor). Treat them identically to the `Number` branch: extract `long millis = ((java.util.Date) val).getTime()` and route through the *same* `calendarDateMillis`/`calendarTimeMillis`/`calendarTimestampMillis(millis, cal)` helpers, merging this case into the `Number` branch (`val instanceof Number || val instanceof java.util.Date`) instead of keeping a separate decomposition path.
      - **Timestamp precision:** `getTime()` truncates to whole milliseconds. After computing the target millis via `calendarTimestampMillis`, construct `new Timestamp(targetMillis)` then call `.setNanos(((Timestamp) val).getNanos())` to restore full nanosecond precision — the zone-offset shift only moves whole minutes/hours, so it never changes the sub-second fraction, meaning the original `nanos` value remains valid after the shift.
    - **`java.time.LocalDate`/`LocalTime`/`LocalDateTime` cells — a third, currently-missing branch, not covered by either the `Number`/`Date` branch or the `String` branch.** `ValueConverter` accepts these directly as cell values, independently of the `String` path: `asSqlDate` accepts `LocalDate` (`Date.valueOf(o)`) and `LocalDateTime` (`Date.valueOf(o.toLocalDate())`, dropping the time-of-day); `asTimestamp` accepts `LocalDateTime` (`Timestamp.valueOf(o)`) and `LocalDate` (`Timestamp.valueOf(o.atStartOfDay())`); `asSqlTime` accepts `LocalTime` (`Time.valueOf(o)`) (confirmed by reading `ValueConverter.groovy:657-663` for `asTimestamp`, `:683-687` for `asSqlDate`, `:739-740` for `asSqlTime`). None of these types are a `Number`, a `java.util.Date` subtype, or a `String`/`CharSequence`, so as drafted above they fall through to the `else` branch (the plain no-`Calendar` conversion) and `cal` is silently ignored for them too — the exact same bug the rest of §2.2 is fixing, just for a third cell-type family. Add explicit branches:
      - `getDate(_, Calendar)`: `val instanceof LocalDate` → use it directly; `val instanceof LocalDateTime` → use `((LocalDateTime) val).toLocalDate()` (matching `asSqlDate`'s own `LocalDateTime` handling, which drops the time-of-day). Then reinterpret in the target zone: `new Date(localDate.atStartOfDay(cal.timeZone.toZoneId()).toInstant().toEpochMilli())`.
      - `getTime(_, Calendar)`: `val instanceof LocalTime` → use it directly. Then reinterpret using the same epoch-date convention `calendarMillis` already uses for its `TIME` case (1970-01-01): `new Time(LocalDateTime.of(LocalDate.of(1970, 1, 1), localTime).atZone(cal.timeZone.toZoneId()).toInstant().toEpochMilli())`.
      - `getTimestamp(_, Calendar)`: `val instanceof LocalDateTime` → use it directly; `val instanceof LocalDate` → use `((LocalDate) val).atStartOfDay()` (matching `asTimestamp`'s own `LocalDate` handling). Then: `Timestamp.from(localDateTime.atZone(cal.timeZone.toZoneId()).toInstant())`.
      - This is the exact same "reinterpret these logical wall-clock fields in the target calendar's zone via `atZone(cal.timeZone.toZoneId())`" operation the parsed-`String` branch already performs on its `LocalDateTime` — a `LocalDate`/`LocalTime`/`LocalDateTime` cell is already a parsed, zoneless wall-clock value, so this branch can skip the text-parsing step and share the same `atZone(...).toInstant()` construction/helper as the `String` branch, rather than duplicating it.
      - **`ZonedDateTime` cells (`getTimestamp(_, Calendar)` only — `asSqlDate`/`asSqlTime` don't accept `ZonedDateTime`):** per the §2.1 decision, discard the embedded zone and reinterpret the local fields in `cal`'s zone — `val instanceof ZonedDateTime` → use `((ZonedDateTime) val).toLocalDateTime()` (matching `asTimestamp`'s own no-`Calendar` handling, `ValueConverter.groovy:660-662`, which already discards the embedded zone the same way), then the identical `Timestamp.from(localDateTime.atZone(cal.timeZone.toZoneId()).toInstant())` construction used by the `LocalDateTime`/`LocalDate` branches above. This is not a separate code path — fold it into the same `LocalDate`/`LocalDateTime` branch by converting `ZonedDateTime` to `LocalDateTime` first via `.toLocalDateTime()`.
      - **Regression test:** a `ZonedDateTime`-typed column (e.g. a cell holding `ZonedDateTime.of(2024, 6, 15, 10, 30, 0, 0, ZoneId.of('America/New_York'))`) — assert `getTimestamp(1, cal)` reinterprets the *local* `2024-06-15T10:30:00` fields in `cal`'s zone (i.e. equals what a `LocalDateTime`-typed cell with those same local fields would produce), **not** the New York instant converted into `cal`'s zone — pinning choice (a) over (b) and preventing a future change from silently flipping the policy.
      - **Regression coverage:** add `Calendar`-shift tests (non-UTC calendar, asserting a real offset vs. the no-`Calendar` getter) for a `LocalDate`-typed column against `getDate`, a `LocalTime`-typed column against `getTime`, and both `LocalDate`- and `LocalDateTime`-typed columns against `getTimestamp` — mirroring the existing `Number`-cell calendar-shift test and the new `String`-cell one. Include these three types in the DST-gap zone-independence test too (§2.2's `TimeZone.setDefault` regression) to confirm the `atZone(cal.timeZone.toZoneId())` construction never consults the JVM default for these cell types either.
    - **Text cells — the `String`-vs-`CharSequence` branch guard is NOT the same for all three getters; `ValueConverter`'s three converters disagree with each other, not just with `LocalDate`/`LocalTime.parse`.** Checked each converter individually (`ValueConverter.groovy:667` `asTimestamp`, `:689` `asSqlDate`, `:732-743` `asSqlTime`):
      - `asTimestamp` and `asSqlDate` each check `instanceof String` specifically and `throw new IllegalArgumentException(...)` for anything else that reaches their final fallthrough — a `StringBuilder`- or `GString`-backed cell (both `CharSequence` but not `String`) is **rejected** by the no-`Calendar` `getTimestamp(int)`/`getDate(int)` today. **For `getDate(_, Calendar)` and `getTimestamp(_, Calendar)`: guard with `val instanceof String` exactly, cast with `(String) val`, do not widen to `CharSequence`** — widening would make these two `Calendar` overloads *more* permissive than their siblings.
      - `asSqlTime`, unlike the other two, has **no type guard at all**: `if (o instanceof Time) return o; if (o instanceof LocalTime) return Time.valueOf(o); return Time.valueOf(String.valueOf(o))` — any object that isn't a `Time`/`LocalTime` falls through to `String.valueOf(o)` (i.e. `o.toString()`), so a `StringBuilder`/`GString` cell **already succeeds** via the no-`Calendar` `getTime(int)` today. **For `getTime(_, Calendar)` only: guard with `val instanceof CharSequence`, convert with `val.toString()`** (not a `String` cast, which would `ClassCastException` on a `StringBuilder`) — matching `asSqlTime`'s actual, broader acceptance. Do not attempt to replicate `asSqlTime`'s fully unrestricted "any `Object` via `toString()`" fallback beyond `CharSequence` — that is a degenerate case (e.g. an `Integer`-typed cell whose `toString()` happens to look like a time) with no realistic use and no existing test coverage; `CharSequence` covers every case a `String`-oriented Matrix column can realistically hold.
      The no-`Calendar` getters otherwise parse **lenient JDBC escape syntax** through the legacy `Date.valueOf(String)`/`Time.valueOf(String)`/`Timestamp.valueOf(String)` methods. **This leniency cannot be safely or exactly replicated by a zone-independent parser — verified empirically that `Date.valueOf`/`Time.valueOf`/`Timestamp.valueOf` accept a materially wider grammar than `LocalDate.parse`/`LocalTime.parse`/a 2-digit-padded custom formatter:**
      | Input | Legacy (`Date`/`Time`/`Timestamp.valueOf`) | `LocalDate`/`LocalTime.parse` or 2-digit-padded formatter |
      |---|---|---|
      | `'2024-2-3'` (single-digit month/day) | `2024-02-03` | throws |
      | `'1:2:3'` (single-digit h/m/s) | `01:02:03` | throws |
      | `'24:00:00'` (time-only) | succeeds, printing as `00:00:00`, but is **not** equal to `Time.valueOf('00:00:00')` — verified empirically the two differ by exactly 24h in `getTime()` millis (the deprecated `Time(h,m,s)` constructor rolls hour 24 into the next calendar day in the JVM default zone; `Time`'s `toString()` just never displays a date part) | throws (`LocalTime` rejects hour 24) |
      | `'2026-4-9 1:2:3'` (single-digit timestamp components) | `2026-04-09 01:02:03.0` | throws |

      **Decision: the `Calendar` overload intentionally accepts a stricter, zero-padded syntax than the no-`Calendar` overload for `String` cells — document and test this divergence rather than attempting to reproduce the legacy leniency.** Reproducing it exactly would mean hand-rolling parsers that replicate each legacy method's specific (and mutually inconsistent — `Time.valueOf('24:00:00')` rolls into the next calendar day internally even though `Time` never displays a date, `Timestamp.valueOf('...24:00:00')` likewise rolls to the next day, `Timestamp.valueOf('2026-04-31 ...')` rolls an invalid date forward into May) wraparound rules while staying provably zone-independent — attempting that produced three rounds of subtle defects in this task even for the narrower strict-format case (the DST-gap issue, the trailing-dot issue, and a `yyyy`+SMART-resolver formatter that silently *renormalized* an invalid date like `'2026-04-31 12:00:00'` to a third, different-again value instead of either matching the legacy rollover or rejecting it). The formatter below (`uuuu` + `ResolverStyle.STRICT`) resolves all of that: it rejects single-digit components, `24:00:00`, and invalid calendar dates outright — a clean, consistent "reject anything not exactly zero-padded and calendrically valid" rule across all three sibling getters, with no remaining asymmetry between them.
      - Date-only: `LocalDate.parse(str)` (ISO built-in) — rejects single-digit components; document this on `getDate(_, Calendar)`.
      - Time-only: `LocalTime.parse(val.toString())` (ISO built-in `LocalTime.parse`, applied to `val.toString()` since the cell may be any `CharSequence`, not only `String` — see the `asSqlTime` guard note above) — rejects single-digit components and rejects hour `24`; document this on `getTime(_, Calendar)`.
      - **Timestamp (`asTimestamp` → `Timestamp.valueOf(String)`): the accepted format is `yyyy-MM-dd HH:mm:ss[.fffffffff]` — a *space* between date and time, not `T`.** The existing test already stores this exact format (`ts: ['2026-04-29 12:34:56']` in `testCalendarGettersConvertStringStoredTemporalValues`). A bare `LocalDateTime.parse(str)` expects `ISO_LOCAL_DATE_TIME` (`T` separator) and **throws `DateTimeParseException` on that value** — do not use it.
      - **Do not route through `Timestamp.valueOf(str).toLocalDateTime()` either — it is *not* zone-neutral at DST gaps, despite parse and decompose happening in the same call.** Verified empirically: with the JVM default set to `Europe/Stockholm`, `Timestamp.valueOf('2024-03-31 02:30:00').toLocalDateTime()` returns `2024-03-31T03:30` (the nonexistent local time — Stockholm's spring-forward gap that day runs 02:00→03:00 — gets normalized *forward* during the `Timestamp` construction step itself, before decomposition even happens); with the default set to `UTC` it returns the unmodified `2024-03-31T02:30`. The two zones disagree because the ambient default is consulted *during encoding*, not only during decoding, so "encode then immediately decode with the same zone" does not cancel out for a wall-clock value that zone doesn't have.
      - **Parse the text directly instead, with no `Timestamp`/`Date`/`Calendar` object involved at any point** — pure text parsing never touches the ambient default. **Use `uuuu` (not `yyyy`) with `ResolverStyle.STRICT`, and `appendFraction(NANO_OF_SECOND, 1, 9, true)` wrapped in `optionalStart()`/`optionalEnd()`:**
        ```groovy
        private static final DateTimeFormatter JDBC_TIMESTAMP_FORMAT = new DateTimeFormatterBuilder()
            .appendPattern('uuuu-MM-dd HH:mm:ss')
            .optionalStart()
            .appendFraction(ChronoField.NANO_OF_SECOND, 1, 9, true)
            .optionalEnd()
            .toFormatter()
            .withResolverStyle(ResolverStyle.STRICT)
        // ...
        LocalDateTime parsed = LocalDateTime.parse(str, JDBC_TIMESTAMP_FORMAT)
        ```
        **`MatrixResultSet.groovy` currently has no `java.time.*` imports at all** (confirmed: its import block only covers `java.sql.*`, `java.math.RoundingMode`, `java.nio.charset.StandardCharsets`, and a couple of `se.alipsa`/`org.apache` types — `java.util.*` is a Groovy default import, which is why `Calendar`/`TimeZone` already resolve unqualified, but `java.time.*` is not a default import). This snippet will not compile as written without adding, at minimum: `java.time.LocalDate`, `java.time.LocalDateTime`, `java.time.LocalTime`, `java.time.Instant` (for the `Timestamp.from(...)` construction), `java.time.format.DateTimeFormatter`, `java.time.format.DateTimeFormatterBuilder`, `java.time.format.ResolverStyle`, and `java.time.temporal.ChronoField`. Add these explicitly to the import list as part of the production-change task (2.2), not left implicit.
        Both pieces matter and were each independently verified empirically to matter:
        - **`optionalStart()`/`appendFraction(1,9,true)`/`optionalEnd()`, not a bare `appendFraction(..., 0, 9, true)`:** the bare form treats the fractional *digits* as optional but still accepts a trailing `.` with zero digits (`'2026-04-29 12:34:56.'` parses successfully, silently dropping the dot), which `Timestamp.valueOf` rejects outright. Wrapping a `1`-minimum-digit `appendFraction` in an optional section makes the whole `.fffffffff` group present-or-absent as a unit, matching `Timestamp.valueOf`'s rejection.
        - **`uuuu` + `ResolverStyle.STRICT`, not `yyyy` with the default SMART resolver:** `yyyy`+SMART does not reject invalid calendar dates, it *silently normalizes them to a different, wrong value* — verified empirically that `'2026-04-31 12:00:00'` (April has 30 days) parses under `yyyy`+SMART to `2026-04-30T12:00` (clamped to the last day of April), while `Timestamp.valueOf('2026-04-31 12:00:00')` normalizes the *same* string to `2026-05-01 12:00:00` (rolls forward into May) — two different legacy-adjacent behaviors, *neither* of which the documented "stricter syntax, reject what's invalid" decision intends; it must simply reject. Using `uuuu` (the era-independent proleptic-year field) with `ResolverStyle.STRICT` fixes this — `withResolverStyle(STRICT)` on a plain `yyyy` pattern was tried earlier and failed even for well-formed input (`yyyy` has a `STRICT`-mode era requirement unrelated to input validity, a known `java.time` pitfall); `uuuu` does not have that requirement. Confirmed empirically with the final `uuuu`+`STRICT` formatter, all prior requirements still hold and the invalid-date case is now correctly rejected: `'2026-04-29 12:34:56'` parses; `'...123456789'` parses with full precision; `'2026-04-29 12:34:56.'`, `'2026-4-9 1:2:3'`, `'2026-04-29 24:00:00'`, and `'2026-04-31 12:00:00'` all throw `DateTimeParseException`; and `'2024-03-31 02:30:00'` (the DST-gap case) still parses to the identical `2024-03-31T02:30` regardless of whether the JVM default is `Europe/Stockholm` or `UTC` — `ResolverStyle` only affects field-range validation during parsing, it does not introduce any timezone lookup.
        - **Bonus consistency from switching to `STRICT`:** the timestamp getter's `24:00:00` handling was previously documented as an accepted asymmetry against the date/time-only getters (`LocalTime.parse` rejects hour `24`, but the old SMART-resolver timestamp formatter accepted it, rolling to the next day like `Timestamp.valueOf`). With `STRICT`, the timestamp getter now also rejects `24:00:00`, so all three sibling getters are mutually consistent — remove that asymmetry note from the divergence documentation and fold `24:00:00` into the ordinary rejection tests for `getTimestamp` too, not only `getTime`.
      - Then build the target instant from the parsed logical fields: `Timestamp.from(parsed.atZone(cal.timeZone.toZoneId()).toInstant())` (note: `Timestamp.valueOf(...)` only accepts a `LocalDateTime`, not a `ZonedDateTime` — it will not compile with a zoned value; go through `Instant` via `Timestamp.from(...)` as shown), and the analogous `Date`/`Time` construction for the date-only/time-only getters. (`atZone` on the *target* calendar's zone — an explicit input, not the ambient default — has its own well-defined, documented gap-normalization behavior per the `java.time` spec; that's expected and fine, since it depends only on the supplied `cal`, never on `TimeZone.getDefault()`.)

## 3. `create()`/`createDdl()` row-scan default: fix the cap where it's safe, leave it alone where it isn't

`DEFAULT_SCAN_ROWS = 100` is meant to cap how many rows are scanned to size `VARCHAR`/`DECIMAL` columns when a caller doesn't pass an explicit `scanNumRows`. All four convenience call sites compute `Math.max(DEFAULT_SCAN_ROWS, table.rowCount())`, which is always `>= table.rowCount()`, so `MatrixDbUtil.createMappings`'s `Math.min(Math.max(scanNumRows, 0), rowCount)` clamp always resolves to the full row count — the cap never engages.

**This is not uniformly a bug — the four call sites split into two different shapes, and naively swapping `Math.max` for `Math.min` everywhere would trade a performance issue for a data-loss/insert-failure issue:**

- **`MatrixSql.groovy:387` (`create(Matrix, String... primaryKey)`), `MatrixSql.groovy:404` (`create(String, Matrix, String... primaryKey)`), and `MatrixDbUtil.groovy:212` (`create(Connection, Matrix, boolean, String...)`)** all build the DDL **and then insert every row of the Matrix** (`MatrixDbUtil.create`, `matrix-sql/src/main/groovy/se/alipsa/matrix/sql/MatrixDbUtil.groovy:76-99`). If sizing is based on only the first 100 rows, a `String` value or `BigDecimal` beyond row 100 that doesn't fit the inferred `VARCHAR`/`NUMERIC` width will fail (or silently truncate, depending on the driver) during the insert that immediately follows. For these three call sites, always scanning the full table is the *correct* behavior, not a bug — do not cap them.
- **`MatrixSql.groovy:434` (`createDdl(Matrix, boolean, int... scanNumrows)`)** only generates DDL text — `matrixDbUtil.createTableDdl(...)` — and never executes it or inserts data. There is no immediate insert to break, so this is the one call site where a genuine sampling cap is safe and matches the method's documented purpose ("obtain sizing info" for a quick DDL preview). This is the actual bug to fix.

3.1 [x] Consolidate the duplicated constant first: remove the private `DEFAULT_SCAN_ROWS` from `MatrixSql.groovy:27` and add a public `static final int DEFAULT_SCAN_ROWS = 100` to `MatrixDbUtil.groovy` alongside its existing `DEFAULT_VARCHAR_SIZE`/`DEFAULT_DECIMAL_PRECISION`/`DEFAULT_DECIMAL_SCALE` constants (~line 28). Update `MatrixSql.createDdl` to reference `MatrixDbUtil.DEFAULT_SCAN_ROWS`. This removes the separate hard-coded `100` literal in `MatrixDbUtil.groovy:212` and the risk of the two drifting apart again.

    - `MatrixSql.groovy:387`: `create(table, table.rowCount(), primaryKey)`
    - `MatrixSql.groovy:404`: `create(tableName, table, table.rowCount(), primaryKey)`
    - `MatrixDbUtil.groovy:212`: `create(con, table, table.rowCount(), addQuotes, primaryKey)`

Where the strict formats *are* well-formed: date-only and time-only strings are ISO-compatible (`LocalDate.parse`/`LocalTime.parse`), but `asTimestamp` parses combined date+time strings via `Timestamp.valueOf(String)`, which requires JDBC escape syntax (`yyyy-MM-dd HH:mm:ss[.fffffffff]`, a *space* separator) — a bare `LocalDateTime.parse` expects ISO `T`-notation and throws on the existing test's `'2026-04-29 12:34:56'` value. **`Timestamp.valueOf(str).toLocalDateTime()` is not a safe substitute either — verified empirically to be default-zone dependent at DST gaps** (`Timestamp.valueOf('2024-03-31 02:30:00').toLocalDateTime()` returns `03:30` under a Stockholm default but `02:30` under a UTC default, because the ambient zone is consulted while *constructing* the `Timestamp`, not only while decomposing it, and a spring-forward gap has no exact millis value to round-trip). **The fix that resolves all of the above: parse with a `DateTimeFormatterBuilder` using `uuuu` (not `yyyy`) + `ResolverStyle.STRICT`, plus `optionalStart()`/`appendFraction(NANO_OF_SECOND, 1, 9, true)`/`optionalEnd()` for the fraction** — confirmed empirically to reject single-digit components, `24:00:00`, the trailing dot, and invalid dates like April 31st, while still correctly parsing well-formed input (fractional seconds included) and remaining fully zone-independent at the DST gap.
