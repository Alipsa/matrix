# matrix-tablesaw v0.4.0 Implementation Plan

## Goal and scope

Deliver the reviewed correctness, security, API-consistency, and I/O fixes for
`matrix-tablesaw` 0.4.0. The baseline is version 0.3.2 on `main`. The findings cover the Groovy
facade, `BigDecimalColumn` and its support classes, and the XML/ODS/XLSX integration layer.

Every finding in the original review was reproduced with a throw-away test or verified against
the implementation and Tablesaw 0.44.4 sources. This plan converts those findings into ordered,
decision-complete work. Unless a task explicitly says otherwise, preserve existing public method
signatures and Tablesaw missing-value conventions.

## Resolved design decisions

- XML containing any `DOCTYPE` is rejected. External general entities, external parameter
  entities, and external DTD loading are also disabled as defense in depth.
- XML sources are closed after parsing, matching the module's existing ODS reader behavior. This
  ownership rule must be documented for `Reader` and `InputStream` sources.
- `Double.NaN` and `Float.NaN` map to a missing `BigDecimalColumn` value. Positive and negative
  infinity are rejected with an `IllegalArgumentException` because `BigDecimal` cannot represent
  them. Finite `Float` values use `new BigDecimal(Float.toString(value))`, preserving the decimal
  form represented by the float rather than exposing binary-to-double widening artifacts;
  `Double` retains `BigDecimal.valueOf(value)` behavior.
- Missing cells are emitted as blank/empty cells by XLSX, ODS, and XML writers. No Tablesaw
  numeric or boolean sentinel is serialized.
- XLSX remains a binary-only format. A writer-backed `Destination` is rejected with a clear
  `IllegalArgumentException`; binary workbook bytes are never transcoded through a `Writer`.
- `BigDecimalColumn` equality is numeric: values for which `compareTo` returns zero are equal.
  Hashing and distinct-value lookup use a canonical `stripTrailingZeros()` key, with zero
  normalized consistently and missing retained as one distinct value. `unique()` and `asSet()`
  both expose the first encountered representation of each numeric value.
- `TableUtil.createColumn` accepts `null` as missing and otherwise requires the runtime type
  appropriate for the requested `ColumnType`. It rejects mismatches with column name, row index,
  expected type, and actual type rather than coercing or silently inserting missing values.
- `TableUtil.round(Column, int)` and `round(NumberColumn, int)` are non-mutating. Numeric inputs
  return a copy; non-numeric inputs remain unchanged as currently documented.
- `BigDecimalColumn.create(String, int...)` is replaced by `createFromInts(String, int...)`.
  `create(String, int)` retains its Tablesaw-compatible meaning of creating that many missing
  rows. This source-incompatible cleanup is allowed by the 0.4.0 version bump.
- No-context `divide` and `divideBy` use `MathContext.DECIMAL64`; overloads accepting an explicit
  `MathContext` are added for callers needing another precision. This is a documented numeric
  behavior change from dividend-scale rounding.
- Empty/all-missing BigDecimal summaries return `null` for mean, median, range, min, and max.
  Coefficient of variation returns `null` when fewer than two non-missing values remain. Sum
  retains its existing empty-input convention.
- XML duplicate column names are compared case-insensitively. With
  `allowDuplicateColumnNames(false)` they are rejected; with it enabled, later occurrences are
  renamed deterministically using a collision-safe `name-2`, `name-3`, ... convention before the
  table is built. All original names are reserved before generated suffixes are allocated, so a
  unique pre-suffixed input remains unchanged.
- The read-option builders remain unchanged in 0.4.0. Their one-line covariant forwarding methods
  must remain for binary compatibility, leaving too little implementation duplication to justify
  a new generic read-builder hierarchy.
- A shared write-option builder owns common destination construction and preserves existing public
  builder entry points and JVM signatures.
- File-backed write builders defer opening their output stream until writing starts. Merely
  creating or building options must not create/truncate a file or leak a file descriptor.

## Execution and completion rules

- Implement sections in numeric order except that the shared write-builder foundation in 8.2 must
  land before the deferred-file work in 4.3. Section 4 keeps its lifecycle regression tests in
  `ExportDataTest`, so it does not depend on the options contract test in 8.3. Sections 2-4 may
  share writer/reader test fixtures, and sections 5-7 may share missing-value helpers, but do not
  duplicate validation or conversion logic.
- Add the regression test before or with each production change. Tests must assert both values
  and missingness where Tablesaw uses sentinels.
- Public classes and methods added or changed in Java require Javadoc; Groovy APIs require
  GroovyDoc with every parameter, default, return value, and exception documented.
- A checkbox remains unchecked until its implementation is present and its relevant test command
  has passed. Record the exact command and result beside the checkbox before marking it complete.
- Use focused tests during development. Before the work is considered complete, run section 10 in
  the repository-required order and record every result here or in the PR description.
