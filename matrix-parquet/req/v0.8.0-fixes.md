# Matrix-Parquet v0.8.0 Fix Plan

## Scope

This plan fixes every finding from the October 2026 `matrix-parquet` review. That includes
items that `req/v0.7.0-fixes.md` and `req/optimized-parquet-review.md` mark as complete but that
are only partly done. Every finding was confirmed against the code at commit `7afb1231`, either by
reading the code or with a throwaway probe test. Three findings could not be fully confirmed and
are marked **(unverified)**.

`matrix-parquet` is already `0.8.0-SNAPSHOT` and `v0.8.0` is unreleased. These fixes therefore go
into the existing `v0.8.0 (unreleased)` section of `release.md` and need no version bump. No git
tag may be created.

A task is done only when its tests pass and the exact commands appear in the verification record
at the end of this file, or in the PR description.

## Compatibility Decisions

### A. Unrepresentable predicate values (section 3)

1. Keep throwing, but throw `IllegalArgumentException` instead of `ArithmeticException`.
   Rejected: `x > 1.5` on an INT32 column is a valid, well-defined predicate.
2. Treat a value that cannot be converted exactly as "not pushable". Keep the predicate as an
   exact residual filter on the decoded value. **Recommended:** results are exact, and the only
   cost is less pruning for these rare predicates.
3. Rewrite to the correct bound (`ceil` for `gt`/`ge`, `floor` for `lt`/`le`; `eq` matches
   nothing) to keep pruning. Deferred: more code and more edge cases. Option 2 can be extended to
   this later without changing behavior.

Choose option 2.

### B. Unsigned integer columns (section 2)

UINT32 reads as `Long` and UINT64 reads as `BigInteger`. UINT8/UINT16 stay `Integer`, since every
value fits. This changes the reported column types for external unsigned files. 0.8.0 is
unreleased, and the old behavior returned wrong values, so no compatibility flag is offered.
Unsigned columns are filtered with residual predicates only, and are not pushed down until a test
proves that parquet-java uses unsigned comparators for record, statistics, dictionary and
column-index filtering.

### C. Nested value types (section 5)

1. Document the loss only. Rejected: a nested `Instant` silently becomes a zone-shifted
   `LocalDateTime`.
2. **Recommended:** write a new footer key, `matrix.nestedTypes`. It is a JSON object that maps a
   nested logical path (the same `col.element`, `col.key`, `col.value`, `col.field` paths used by
   `decimalMeta`) to the canonical Matrix class name. Only write a path when its class differs
   from the reader's default inference for that leaf. The reader passes these expected classes
   to the nested converters. Files without the key keep today's inference.

Choose option 2. Older readers ignore unknown keys, so the format stays backward compatible.

**Path escaping (review fix, 2026-10-18):** each path segment has `.` and `\` escaped
(`\..` → `\.`, `\` → `\\`), so dotted column or struct-key names cannot collide with the
path separator (e.g. top-level `s.a` vs struct `s` child `a`). The writer also drops a
nestedTypes entry if the same path is ever recorded with different types, and the reader
only applies nestedTypes to leaves that are not top-level columns.

### D. Sub-microsecond timestamps (section 8.1) — **decided by the maintainer, 2026-10-18**

**Decision:**
- The default unit is microseconds: `timestampUnit: 'MICROS'`, written as
  `TIMESTAMP(MICROS, adjusted=true)`.
- Sub-microsecond digits are truncated, without an error, for `LocalDateTime`, `Timestamp` and
  `Instant` alike.
- The current `Instant` rejection is a bug and is removed.
- Full precision is available with the opt-in `timestampUnit('NANOS')`.

**Range-check extension (review fix, 2026-10-18):** `ColumnTypePolicy.resolve` now runs the
same `TemporalUnits.epochUnits` overflow check for `LocalDateTime` (using the writer's pinned
zone) and `Timestamp` as it already did for `Instant`, so NANOS overflow fails at schema
validation instead of partway through the row loop.

**Context:**
- Before this change, `LocalDateTime` and `Timestamp` were silently truncated while `Instant` was
  rejected (`ColumnTypePolicy.groovy:43`, `ParquetValueWriter.groovy:141-143`).
- Clock precision decides who is affected:
  - macOS JDK 21 measured microseconds here (`2026-10-18T10:27:08.024084Z`), so `now()` values
    there lose nothing.
  - Since JDK 15 (JDK-8242504) the Linux system clock has nanosecond precision. This was not run
    here.
  - Windows clocks have 100 ns resolution.
- Under the old rule, `Instant.now()` columns therefore already failed on Linux.

**Why truncate rather than reject:**
- A strict default would make ordinary `now()`-based writes fail on Linux and Windows servers.
- Microseconds are the widest-supported Parquet timestamp unit: Spark reads TIMESTAMP(NANOS)
  poorly.
- Truncation drops less than one microsecond, and only where the platform clock is finer than
  microseconds.

**Exception to v0.7.0:** this is a deliberate exception to the "lossless by default" rule adopted
for decimals in `v0.7.0-fixes.md` (Compatibility Decision, option 2). Decimal rounding can change
values by whole units of the declared scale. Timestamp truncation is bounded below one
microsecond.

**Truncation semantics:**
- Digits are always discarded downward in time, because `Instant`/`LocalDateTime` nanos are
  non-negative, including before 1970.
- `LocalDateTime` is converted to an instant with the writer zone first, then truncated.
- int64 overflow is still rejected with column/row context under both units. Under `NANOS` the
  representable range is only 1677-09-21T00:12:43.145224192Z to 2262-04-11T23:47:16.854775807Z.

**Known consequence (documented, tested in §8.4):** under `MICROS`, filtering with the exact
sub-microsecond value that was written finds nothing. For example, after writing `Instant.now()`,
`eq('ts', sameInstant)` returns 0 rows, because the stored value was truncated and predicates are
evaluated exactly (decision A). This is logically correct but surprising, so the readme explains
it and shows `truncatedTo(ChronoUnit.MICROS)` and `timestampUnit('NANOS')` as the fixes.

**Rejected alternatives (kept for future reviewers):**
1. Reject sub-microsecond values for all three classes (strict, lossless): breaks `now()` on Linux
   and Windows.
2. Keep the inconsistent status quo (truncate two classes, reject `Instant`).
3. A strict opt-in flag (for example `rejectTimestampTruncation(true)`): deferred until a user asks
   for it. It can be added later without changing the default.

**Required documentation** so users and future reviewers are not surprised:
- GroovyDoc on `ParquetWriteOptions.timestampUnit`, `WriterBuilder.timestampUnit` and the
  `MatrixParquetWriter` class Javadoc (§14.1);
- the readme type table and a dedicated "Timestamp precision" paragraph (§14.2);
- a `release.md` row (§14.3);
- a code comment at the truncation site that points to this decision.

### E. INT96 timestamps (section 12)

`release.md` currently documents INT96 as a contextual unsupported-type error. Change this to
read-only support: decode INT96 as an adjusted (UTC) instant. Return it as `LocalDateTime` in the
reader zone, the same as other adjusted timestamps. Return `Instant`/`Timestamp`/`Date` when
compatible Matrix metadata asks for them. The writer never emits INT96. FLOAT16 stays unsupported.

holds `Long` values, or wrong signed values if the widening is skipped.

  `LocalDateTime`/`Timestamp`/`Instant`.

  `ParquetValueWriter.groovy:141-143`.
- Under `MICROS`, truncate sub-microsecond digits for all three classes. The existing
  `instantToMicros` already discards them, so after removing the check the behavior is the same
  for all three (it is replaced by the shared helper below, which also truncates). Add a comment
  at the helper: "Sub-microsecond digits are intentionally truncated
  under MICROS; see req/v0.8.0-fixes.md decision D."
- Keep the int64 overflow check for both units (`ColumnTypePolicy.groovy:44-45` becomes
  unit-aware and calls the shared helper below), and extend it to `LocalDateTime` (after zone conversion) and `Timestamp`, with
  column/row context. For `LocalDateTime`, the zone-dependent overflow check can happen in
  `ParquetValueWriter`, where the zone is known.
- All epoch-unit conversions go through one shared helper, for example
  `TemporalUnits.epochUnits(Instant, TimeUnit)`. There are four call sites, and none may keep the
  naive formula:
  1. `ColumnTypePolicy.groovy:44-45`, the overflow check at schema-building time. It runs before
     any value is written, so a naive check here would reject the NANOS lower bound before the
     writer is reached;
  2. the `MICROS` writer path, `ParquetValueWriter.instantToMicros` (`:163`). Delete it and call
     the helper directly;
  3. the new `NANOS` writer path;
  4. `ParquetPredicate.physicalValue` (`:178`), see below.

  The naive
  `addExact(multiplyExact(epochSecond, 1_000_000_000L), nano)` overflows at the lower NANOS bound:
  `1677-09-21T00:12:43.145224192Z` has `epochSecond = -9223372037`, and the intermediate product
  is below `Long.MIN_VALUE` even though the final value (`Long.MIN_VALUE`) fits. For negative
  `epochSecond`, compute `addExact(multiplyExact(epochSecond + 1, unitsPerSecond),
  nano.intdiv(nanosPerUnit) - unitsPerSecond)`; otherwise
  `addExact(multiplyExact(epochSecond, unitsPerSecond), nano.intdiv(nanosPerUnit))`. Verified
  with a JDK 21 probe: the naive form throws `long overflow` at the minimum; the split form gives
  exactly `Long.MIN_VALUE`/`Long.MAX_VALUE` at the bounds, throws one nanosecond outside either
  bound, and gives `-500000000` for `1969-12-31T23:59:59.5Z`. The `MICROS` path has the same
  overflow at its lower bound, `-290308-12-21T19:59:05.224192Z` (`epochSecond = -9223372036855`):
  a second probe showed the naive form throws and the split form gives `Long.MIN_VALUE`. The
  upper bound is `+294247-01-10T04:00:54.775807Z`.
- The helper **truncates** sub-unit digits (`nano.intdiv(nanosPerUnit)`, which floors because
  `nano` is never negative). It does not check for loss; that is the caller's job.
- Use the same helper in `ParquetPredicate.physicalValue` (`:178`, which today has the same naive
  formula). Otherwise an exact predicate on the NANOS lower bound silently becomes
  `NOT_PUSHABLE` under decision A: results stay correct but pruning is lost.
- `physicalValue` must keep its lossy check, `instant.nano % nanosPerUnit != 0` →
  `NOT_PUSHABLE`, **before** calling the helper. The residual predicate re-checks every row
  that the pushdown keeps (`ParquetBatches.groovy:69,180`), but it cannot bring back rows that
  the pushdown dropped. So a truncated push is wrong whenever it drops a matching row. Example:
  a MICROS column stores S = `.123456`, the predicate value is V = `.123456789`, and its
  truncated value is T = `.123456`. Stored values have whole-microsecond precision, so for a
  stored R, `R <= V` is the same as `R <= T`:
  - `lt` is the only operator that breaks. Exact `S < V` is true, but the pushed `lt(T)` drops S;
  - `le(T)` keeps exactly the matching rows, and `gt(T)` is exact for the same reason;
  - `eq(T)` and `ge(T)` keep a superset, which the residual narrows;
  - `ne` and `not` are never pushed (`ParquetPredicate.groovy:108` returns `null` for `ne`
    before computing a physical value, and `not` falls through to `default -> null` at `:102`).

  The check stays mandatory for every operator. Only `lt` fails today, but that depends on how
  each operator happens to be built, and a later change (pushing `not`, for example) would break
  silently.
- Pass the unit through `ColumnTypePolicy` and `ParquetValueWriter` as a parameter, not a
  ThreadLocal.
- Reader: TIMESTAMP(NANOS) is already decoded by `timestampInstant`. Confirm that
  `ParquetPredicate.physicalValue` handles NANOS columns, and add a predicate test.
- Unit-test the helper directly for MILLIS/MICROS/NANOS: at the NANOS bounds, one nanosecond

9.3 [x] **(unverified on Windows)** Rewrite `globFiles` (`MatrixParquetReader.groovy:827-838`).
Put the parsing in a package-scope `GlobSpec parseGlob(String pattern, String separator)` so it can
be tested on any OS.

`GlobSpec` holds the literal root string, the matcher pattern string, the walk depth (or
unlimited), and a flag saying whether any wildcard or escape was present.

- **Escapes and separators per OS.**
  - On every platform, the JDK glob syntax (`FileSystem.getPathMatcher` Javadoc) treats `\` as an
    escape character, not a separator. Its Windows example is `C:\\*`.
  - On Windows (`separator == '\\'`), `\` in a user pattern means a path separator, so **glob
    escaping is not supported on Windows**; document this. `parseGlob` converts every `\` to `/`
    in the pattern before any further processing. The Windows glob treats `/` as a separator,
    and `Path.of` accepts `/` on Windows.
  - On POSIX (`separator == '/'`), `\` stays the glob escape: `\*` and `\{` are literals.
- **Root split.** After the Windows conversion, scan for the first *unescaped* metacharacter
  (`*`, `?`, `[`, `{`). The root is the prefix up to the last `/` before it.
  - Keep that `/` in the root when the prefix would otherwise be empty or end in `:`, so the
    root is the filesystem root and not the current directory: `/*.parquet` → root `/` (today's
    code does this with `Math.max(1, slash)`, `MatrixParquetReader.groovy:833`), and
    `C:\*.parquet` → `C:/` rather than the drive-relative `C:`;
  - If there is no `/` at all before the first metacharacter (for example `*.parquet`), the root is
    the current directory, `Path.of('.')`, and the whole pattern is the relative pattern.
    Probed on macOS/JDK 21: walking `.` yields `./a.parquet`, `root.relativize(p)` gives
    `a.parquet`, and `glob:*.parquet` matches it (`Path.of('')` behaves the same).
  - On Windows, a drive-relative pattern such as `C:*.parquet` (no separator after the drive)
    is rejected with `IllegalArgumentException("Drive-relative glob not supported ...")`.
    Treating it as `.` would match nothing, because relativized paths never start with `C:`.
    Not verified on Windows; covered only by the `parseGlob` unit test below.
  - The root's literal text is unescaped (`\x` becomes `x`) before it goes through `Path.of`.
  - If the pattern has no unescaped metacharacter but contains a POSIX `\` escape (for example
    `root/x\*.parquet`), the whole pattern is still a glob: the root is the prefix up to the last
    `/` and the matcher gets the rest. It is not treated as a literal path, because
    `Path.of('root/x\*.parquet')` would look for a file name containing a backslash.
  - Only a pattern with neither metacharacters nor escapes is a plain file path, which is
    today's behavior.
- **Matching.** Build the matcher from the *relative* pattern part, after the Windows
  conversion, with `FileSystems.default.getPathMatcher("glob:" + relativePattern)`. Match it
  against `root.relativize(p)` as a `Path`. No `/` joining and no second `Path.of` on the
  pattern are needed.
- **Depth.** Let `separators` be the number of unescaped `/` in the relative pattern outside
  `[...]`; the walk depth is `separators + 1` (the number of segments in the relative pattern).
  Use `Files.walk(root, separators + 1)`. Fall back to an unlimited walk when the pattern contains `**`,
  or when any `{...}` alternative contains a `/`, for example `{a,b/c}`. In both of those cases
  the depth is not fixed.
- **Errors.** A missing literal root gives `IllegalArgumentException("No such glob root ...")`.
  An empty match gives `IllegalArgumentException("No files match glob '...'")` instead of the
  generic dataset message.

Tests (POSIX run):
- a deep tree where `root/*.parquet` must not descend (assert via results, and that the walk is
  depth-limited through a spy or a large decoy tree);
- `root/**/*.parquet`;
- `root/{a,b/c}/*.parquet` matches both depths;
- `root/x\*.parquet` (no unescaped metacharacter) matches only the literal file `x*.parquet` and
  not `xy.parquet`. This needs a POSIX file name containing `*`; use `assumeTrue` where the file
  store rejects it;
- `root/a\{b\}/*.parquet` resolves the literal directory `a{b}` as the root;
- a missing root; no matches.

`parseGlob` unit tests with `separator = '/'`:
- `*.parquet` → root `.`, pattern `*.parquet`, depth 1;
- `{a,b}/*.parquet` → root `.`, pattern `{a,b}/*.parquet`, depth 2;
- `/*.parquet` → root `/`, pattern `*.parquet`, depth 1.

`parseGlob` unit tests with `separator = '\\'`, which run on any OS:
- `C:\data\*.parquet` → root `C:/data`, matcher pattern `*.parquet` (no backslashes left), depth 1;
- `C:\data\sub\*.parquet` → root `C:/data/sub`, pattern `*.parquet`. Before the conversion was
  added, this case produced `sub\*.parquet` with an escaped `*`, which matches nothing;
- `C:\data\{a,b}\*.parquet` → root `C:/data`, pattern `{a,b}/*.parquet`, depth 2;
- `C:\data\**\*.parquet` → unlimited depth;
- `C:\*.parquet` → root `C:/`, pattern `*.parquet`, depth 1;
