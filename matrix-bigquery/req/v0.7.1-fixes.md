# matrix-bigquery v0.7.1 reliability fixes plan

This plan addresses the data-integrity, request-size, serialization, error-handling, and
documentation defects identified in the v0.7.1 review. The write-path changes come first because
they can otherwise duplicate or reject user data.

## 0. Compatibility decision

Keep this work in v0.7.1. `BqInsertResult` and `insertRows(...)` are additive, while every existing
`insert(...)` signature and its return type remain available for source and binary compatibility.
Those old methods will be deprecated and will literally continue to return `null` after a successful
`InsertAll` write, matching their existing de-facto behavior; callers needing an outcome must use
`insertRows(...)`. Avoiding an automatic retry after an ambiguous write-channel failure is a
data-integrity bug fix, and batching is transparent except that it permits previously oversized
writes to succeed. Record these semantics prominently in the release notes and migration guidance.

0.1 [ ] Retain the v0.7.1 version and implement the additive `insertRows(...)` migration path
without removing or changing the parameter or return types of the existing `insert(...)` methods.

## 1. Make write-channel fallback safe and bounded

The current fallback retries every connection failure through `InsertAll`. A failure after the
write-channel service has accepted the upload can therefore insert the same append batch twice.
The fallback also constructs one unbounded `InsertAllRequest`, which fails once its encoded payload
exceeds BigQuery's request limit.

1.1 [ ] Refactor `insert`, `insertViaWriteChannel`, and `insertViaInsertAll` in
`matrix-bigquery/src/main/groovy/se/alipsa/matrix/bigquery/Bq.groovy` so that, on every write-channel
connection failure, they use the `JobId` already created before the channel is opened to call
`bigQuery.getJob(jobId)`. Do not classify failures by the helper or line that threw: upload
finalization in `json.close()` is ambiguous and is intentionally covered by this rule.

1.2 [ ] Define package-scoped `JOB_LOOKUP_GRACE_ATTEMPTS = 10` and
`JOB_LOOKUP_GRACE_INTERVAL_MS = 1_000`, giving a maximum 10-second grace period after the first
`getJob(jobId)` returns `null`. Implement the re-check helper with package-visible configurable
attempt and interval values so tests can use short limits without sleeping. If any lookup returns a
job, call `waitFor()` and return that job's successful or failed outcome without submitting
`InsertAll`. Only after every grace lookup remains `null` may the operation fall back once to
`InsertAll`. If job lookup throws, `waitFor()` returns `null`, or waiting cannot establish an
outcome, throw a `BqException` stating that the write outcome is unknown and must not be retried
automatically. State the real 10-second bounded residual race explicitly in the release note rather
than representing a single null lookup as proof.

1.3 [ ] Preserve `append=true` and `append=false` semantics in the only permitted fallback path:
prepare the target through the current `prepareInsertAllTargetTable` flow, then submit `InsertAll`
once only after the `JobId` lookup was `null`. In the release notes, document the existing BigQuery
streaming-buffer caveat for `append=false` when that preparation recreates or truncates a table
(rows may be temporarily rejected); do not silently claim overwrite is immediately streamable.

1.4 [ ] Generate a per-`insertRows(...)`-invocation operation salt once, and create each
`RowToInsert` with `RowToInsert.of(insertId, content)`. Use the fixed layout
`v1:<project>.<dataset>.<table>:<globalRowOffset>:<invocationSalt>`, populated from the canonical
`TableId`, so library-internal retries within one invocation reuse exactly the same IDs. Expose the
package-scoped ID formatter or salt supplier for a fixed-salt unit test. A caller that deliberately
invokes `insertRows(...)` again receives fresh IDs; this is consistent with 1.2 forbidding automatic
re-submission after an unknown outcome. Treat BigQuery's best-effort, roughly one-minute insert-ID
deduplication window only as secondary protection; the no-automatic-retry rule is the correctness
guarantee.

1.5 [ ] Replace the single `InsertAllRequest` construction with ordered batches. Define
package-scoped defaults `INSERT_ALL_TARGET_REQUEST_BYTES = 5 * 1024 * 1024`,
`INSERT_ALL_DEFAULT_MAX_ROWS = 500`, and `INSERT_ALL_HARD_MAX_ROWS = 50_000`; 500 is BigQuery's
recommended request size and 50,000 its hard row limit. Use the hard limit to validate every
package-scoped test or production override of the default row cap. JSON-encode each normalized row
map as UTF-8, add a fixed per-row request-envelope allowance (insert ID, `json` wrapper, commas,
and array delimiters), and flush a normal batch before it reaches the 5 MiB target. This deliberately
serializes each row twice (for estimation and the client request), an acceptable cost for bounded
streaming inserts. Reject any estimated request at or above BigQuery's 10 MB limit with a contextual
`BqException`; permit a single 5--10 MB row only as its own request. Expose the batching
helper/configuration package-wide so tests can supply tiny byte and row limits rather than
constructing 10 MB fixtures.

1.6 [ ] Build and submit one batch at a time, retaining only the current converted batch in memory,
and include the original Matrix row offset in each batched `InsertAllResponse` error message.

1.7 [ ] Add focused unit tests in
`matrix-bigquery/src/test/groovy/se/alipsa/matrix/bigquery/InsertAppendSemanticsTest.groovy` for:

1.7.1 [ ] a connection failure whose grace lookups all return `null`, using short injected grace
limits and followed by one safe fallback;
1.7.2 [ ] a connection failure with a returned job that waits for and returns that job's outcome
without another submission;
1.7.3 [ ] a first `null` lookup followed by a job on the second short-grace lookup, plus job-lookup
and job-wait failures; all must avoid another submission when an outcome may exist;
1.7.4 [ ] `append=false` and `append=true` on the permitted fallback path;
1.7.5 [ ] multiple batches with correct ordering, configured small batch sizes, global error row
indices, and size estimates derived from the normalized row map used by both write paths; and
1.7.6 [ ] the exact `v1:project.dataset.table:7:test-salt` insert-ID format, reuse across
library-internal retries in one invocation, and fresh IDs after a caller creates a second invocation,
without asserting BigQuery deduplication behavior.

1.8 [ ] Extend the BigQuery-emulator coverage in
`matrix-bigquery/src/test/groovy/test/alipsa/matrix/bigquery/BqTestContainerTest.groovy` to exercise
multi-batch overwrite and append writes with `bigquery.enable_write_api=false`.

## 2. Align fallback schema mapping with JSON serialization

`TypeMapper` maps unrecognized Java classes to `STRING`, but the write-channel serializer delegates
those values to a Jackson generator without an object codec. Common Matrix values such as `UUID`,
enums, lists, and maps therefore fail despite the advertised STRING fallback.

2.1 [ ] Define and document the supported `STRING` fallback policy in
`matrix-bigquery/src/main/groovy/se/alipsa/matrix/bigquery/TypeMapper.groovy`: scalar unknown values,
including `UUID`, use `String.valueOf(value)`; enums use `name()`; and `List`/`Map` values use JSON
text produced by `groovy.json.JsonOutput.toJson(value)`, preserving a round-trippable JSON
representation without adding a Jackson 2/3 coupling. Declare the catalog's existing `groovy-json`
alias explicitly in `matrix-bigquery/build.gradle`; do not reuse the Jackson 3 `tools.jackson`
aliases or rely on the Google client's transitive Jackson 2 libraries. ARRAY, STRUCT, and BigQuery
JSON support remain explicit future schema mappings rather than accidentally emitted nested values.
Document in `TypeMapper` GroovyDoc that this nested fallback uses `JsonOutput`'s own serialization:
it does not apply the top-level BigQuery-safe temporal or decimal formatting from 2.4. In particular,
nested `java.time` values may be bean-property JSON, `Date` uses `JsonOutput`'s ISO form, and
`BigDecimal` is a JSON number; callers who require BigQuery-compatible nested values must normalize
them before insertion.

2.2 [ ] Extract one shared value-normalization helper in
`matrix-bigquery/src/main/groovy/se/alipsa/matrix/bigquery/Bq.groovy` and use it from both
`writeJsonValue` and `convertRowForInsertAll`, so the write channel and `InsertAll` serialize the
same Matrix value identically.

2.3 [ ] Change the final `writeJsonValue` branch to write the normalized fallback as a JSON string
instead of calling `JsonGenerator.writeObject` without an `ObjectCodec`.

2.4 [ ] Retain the existing special handling for numeric, boolean, byte-array, date/time, and null
values, including BigQuery-safe decimal and temporal formatting.

2.5 [ ] Add regression tests in `TypeMapperTest.groovy` and a focused Bq serialization test for
`UUID`, an enum, `List`, and `Map`; assert exact scalar and enum-name values and `JsonOutput`
JSON-text values (using ordered maps and nested strings, booleans, and integers only) on both write
paths, as well as the absence of `No ObjectCodec defined` failures. Do not make these fallback tests
depend on `JsonOutput` representations of nested temporal, decimal, or arbitrary object values.

## 3. Replace the invalid InsertAll statistics contract

`createPlaceholderLoadStatistics` returns `null`, because a locally-built `JobInfo` has no completed
job statistics. The API currently promises a `LoadStatistics` object and causes callers to fail when
they use it after an `InsertAll` write.

3.1 [ ] Introduce a public result type (for example, `BqInsertResult`) that reports the requested
row count, successful row count where known, write mechanism, optional write-job ID, and optional
`LoadStatistics`.

3.2 [ ] Add `BqInsertResult insertRows(Matrix matrix, TableId tableId, boolean append)` and explicit
convenience overloads with distinct signatures: mirror the current `(Matrix, String)` and
`(Matrix, String, String, boolean)` shapes, but avoid Groovy default arguments that would generate
ambiguous synthetic overloads. Route all implementations through `insertRows(...)`. Document that
`loadStatistics` exists only for write-channel load jobs. Deprecate the existing `insert(...)`
overloads without changing their signatures: after a successful `InsertAll` path they return `null`
literally, while a write-channel path returns its real `LoadStatistics`.

3.3 [ ] Remove `createPlaceholderLoadStatistics` and update Javadoc, README examples, and tests to
use the result type when callers need write outcome metadata.

3.4 [ ] Add tests proving `insertRows(...)` returns a non-null `BqInsertResult` with absent
`loadStatistics` after `InsertAll`, that the deprecated `insert(...)` bridge returns `null` on that
same path, and that a write-channel success exposes its actual statistics through both APIs.

## 5. Correct the type-mapping documentation

The implementation stores `ZonedDateTime` as ISO-8601 text in a `STRING` column, but the tutorial
and cookbook claim it maps to `TIMESTAMP`. A BigQuery TIMESTAMP represents an instant and does not
retain the original zone identifier, so the documentation must describe the selected preservation
policy accurately.

5.1 [ ] Update `docs/tutorial/12-matrix-bigquery.md` and
`docs/cookbook/matrix-bigquery.md` to state that `Instant` and `Timestamp` map to `TIMESTAMP`, while
`ZonedDateTime` maps to `STRING` and retains its ISO-8601 zone representation.

5.2 [ ] Add a brief concrete round-trip example showing both an `Instant` and a `ZonedDateTime`,
including the resulting BigQuery column types and the zone-preservation trade-off.

5.3 [ ] Reconcile `matrix-bigquery/readme.md`, `Bq` GroovyDoc, and `TypeMapper` GroovyDoc with the
same mapping table.

5.4 [ ] Add a schema-creation regression assertion in `SchemaCreationTest` that
`TypeMapper.toStandardSqlType(ZonedDateTime)` is `StandardSQLTypeName.STRING`.
